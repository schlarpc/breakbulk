# Target traits and presets

Target traits are the facts about a target triple that breakbulk needs (OS, object format, file names); every per-target decision reads them instead of matching the triple's spelling. Presets turn those facts and a few options into a target's toolchain. This page covers both, then each preset's details.

## Target traits

Every decision that depends on the target platform reads one record, the target's **traits**, made by one function (`breakbulk.targetTraits.resolve`, `lib/target-traits.nix`). No other code inspects how a triple is spelled. This follows the linker choice (`lib/presets/linker.nix`): a decision is a function of facts, and the facts have one home.

- **Base fields** are what rustc's own cfg says about the target: `vendor`, `os`, `env`, `abi` and `families` (`target_vendor`, `target_os`, `target_env`, `target_abi`, `target_family`), plus `arch`, the triple's first component as spelled (`i686`, `armv7`, `riscv64gc`, not `target_arch`: the tool names below are derived from that spelling). `parse` reads them from a built-in target name. The check `target-traits-rustc` compares it with `rustc --print cfg --target <t>` for every built-in target of nixpkgs' rustc: 248 of 321 are known, all agreeing (the abi only where the name spells one; rustc infers powerpc64's `elfv1`/`elfv2`). The rest (RTOSes such as nuttx, vxworks, qnx; `.json` target specs) return null.
- **Derived fields** follow from the base fields: `kernel` (`linux` for `linux` and `android`, `darwin` on Apple, the OS for other OSes with their own kernel, null for bare metal, UEFI, wasm and CUDA) for kernel-level facts; `isLinux` (a Linux userland: os `linux`, so not Android, Android targets have no linker rule and fail at evaluation naming issue #27 until an NDK preset exists), `isWindows`, `isMsvc`, `isMingw` (Windows with env `gnu`, so `-gnullvm` too), `isApple`, `isWasm`, `isWasi`, `isBareMetal`, `isUefi`; `linksComponents` (the link writes a WebAssembly component: WASI from preview 2 on, whose specs name `wasm-component-ld` as the linker); `objectFormat` (`elf`, `pe`, `macho`, `wasm`, `xcoff` on AIX); `executableSuffix`, `sharedLibraryPrefix`/`sharedLibrarySuffix`, `staticLibraryPrefix`/`staticLibrarySuffix`, rustc's target-spec `exe_suffix`, `dll_prefix`/`dll_suffix` (dylib and cdylib) and `staticlib_prefix`/`staticlib_suffix`, which `target-traits-rustc` compares with `rustc --print file-names --crate-type <t>` for every built-in target it knows (all 248 agree; a crate type rustc drops for a target is skipped); `debugArtifacts`, the debuginfo files a link writes that `--print file-names` does not name, as a list of `{ suffix; when; perObject ? false; directory ? false; }`: msvc and UEFI `[ { suffix = ".pdb"; when = "always"; } ]` (rustc links both with an MSVC-style linker, UEFI with rust-lld as lld-link, which writes it for every linked crate whatever `-C debuginfo` says), Linux and Android userlands `[ { suffix = ".dwp"; when = "split-packed"; } { suffix = ".dwo"; when = "split-unpacked"; perObject = true; } ]` (the targets whose rustc spec supports split debuginfo: not riscv, unikraft or WALI, nor other ELF targets such as the BSDs and bare metal), Apple `[ { suffix = ".dSYM"; when = "split-packed"; directory = true; } ]`, else none. `target-traits-rustc` compares `objectFormat`, `isApple`, `isWasm`, `isMsvc`/`isUefi` (an MSVC-style linker), `linksComponents` and `debugArtifacts` with `rustc --print all-target-specs-json` for every built-in target it knows (all 255 agree); `dylibPathVar` and `dylibPathSep` (Cargo's `dylib_path_envvar` for a process running natively on the target: `PATH` on Windows, `DYLD_FALLBACK_LIBRARY_PATH` on Apple, `LD_LIBRARY_PATH` elsewhere, null for wasm and bare metal); [`debugInfo`](../../reference/options/targets.md#targetsnamedebuginfo)

  (the default of `targets.<t>.debugInfo`, `split` on a Linux ELF target, `keep` elsewhere).
- **Tool names** are derived fields too: the target as each tool spells it, so no preset translates a triple itself.
  - `nixpkgsSystem`: the nixpkgs platform of the target's package set, a `pkgsCross` attribute name (from a table in `lib/target-traits.nix`, for the platforms Hydra builds, and caches) or a `crossSystem` attribute set, `{ config = <the triple with nixpkgs' CPU name>; }` (riscv64gc as `riscv64`, armv7 as `armv7l`). `presetHelpers.targetPkgsFor pkgs traits` imports nixpkgs with it, and `targetTraits.nixpkgsPlatform traits` elaborates it. A platform nixpkgs rejects (thumbv7neon, say) fails there, naming this trait and the preset's `packageSet`. The check `target-traits` elaborates every table entry and some fallbacks, and compares nixpkgs' `rust.rustcTarget` with the triple ([G5](../../reference/assumptions.md#g5-tool-name-traits-are-nixpkgs-and-the-tools-spelling)).
  - `zigArch`: `zig cc -target`'s architecture (`linuxPortable`): i686 as `x86`, riscv64gc as `riscv64`, armv7 as `arm`.
  - `qemuArch`: qemu-user's program suffix (`qemu-<arch>`, the `qemu-user` runner), nixpkgs' `qemuArch` for the same platform: i686 as `i386`, powerpc64le as `ppc64le`.
  - `xwinArch`: the msvc SDK's library directories (`sdk.libDirs.<arch>`, the `windows` preset for `-msvc`): `x86`, `x86_64`, `aarch` (thumbv7a), `aarch64`; null for other targets.

  Set one in `targets.<triple>.traits` where a tool spells the target otherwise, e.g. `nixpkgsSystem = { config = "armv7l-unknown-linux-gnueabihf"; gcc.fpu = "neon"; };`.
- **Who reads them:** the linker kind (`linkerKind`), the test runner kind (`runnerKind`) and the test process's dynamic-library variable (`testRuns.dylibPathOf`), static linking (`staticLinking`), the default debug handling and so the debug stage, remap scope and build ID (`lib/products.nix`), the install layout (`install`, `splitDebug`'s placement of side files) and the names of root files (`rootFiles`). These are all read at evaluation time. A fact read only at plan or build time comes from rustc instead, so it needs no traits and is never wrong for a custom target: the planner reads the executable suffix and which units get a `debug` output from its rustc's target spec ([Target facts from rustc](planner.md#target-facts-from-rustc)), and the installed test, bench and bin executables take their suffix from the unit's own file name. The Rust programs never parse a triple and receive no traits. Evaluation-time facts cannot come from rustc the same way: a probe would add an import-from-derivation per target to dynamic-derivation mode, and evaluating another system's outputs would need a builder for it.
- **Bring your own target.** [`targets.<triple>.traits`](../../reference/options/targets.md#targetsnametraits) (and `workspaces.<ws>.targets.<triple>.traits`) is an attribute set merged over the built-in traits: base fields recompute the derived ones, and derived fields set there win. A name that is not a trait is an evaluation error listing the known ones. A triple with no built-in traits (a custom target, a `.json` spec) needs at least the base fields:

  ```nix
  targets."thumbv7em-myboard-none" = {
    traits = { os = "none"; abi = "eabihf"; };
    linker = "${myToolchain}/bin/arm-none-eabi-gcc";
  };
  ```

  Without them, reading any trait of that target fails with a message naming `targets."<triple>".traits`. A custom triple also has no nixpkgs package set of its own (its `nixpkgsSystem` is `{ config = <triple>; }`, which nixpkgs may not parse): set `traits.nixpkgsSystem` when its packages have library inputs, or give the package set directly: [`targets.<triple>.packageSet`](../../reference/options/targets.md#targetsnamepackageset), which the Linux and MinGW presets read. The failure is lazy: a target whose traits nothing reads (one with an explicit linker and no default stages) still plans and builds its units. Its products read the file-name and layout fields (`rootFiles`, `install`, `packDwo`) at evaluation time, so they need them ([A custom target](../../how-to/targets.md#a-custom-target)). The resolved record is `repo.workspaces.<ws>.target.<triple>.traits`, and the value of the target spec's `traits` option, which presets read as `config.traits`.

## Toolchain presets

The LLVM version matching rustc comes from `rustc.llvmPackages` only for nixpkgs' own rustc; rust-overlay and fenix toolchains do not carry it. The library ships a table from Rust version to LLVM major version, overridable per toolchain (`llvmMajor`, `llvmPackages`).

The table is the fast path; for a rustc it does not cover (older than its first release, newer than the last release checked, or without a version), a tiny derivation reads the major from `rustc -vV`, through import-from-derivation.

Every fact about a toolchain comes from one function, `breakbulk.toolchainFacts.of { pkgs; rustc; }` (`lib/toolchain-facts.nix`): `version`, `majorMinor`, `llvmMajor`, `wasiSdkVersion` and `capabilities` (see [Toolchain capabilities](planner.md#toolchain-capabilities)), each from the toolchain's attributes and breakbulk's tables when they can say, else from one `rustc -vV` probe (release and LLVM major), so the wasi-sdk choice now also works for a rustc without a `version` attribute.

`llvmVersions.packagesFor` and `wasiSdk.sysrootFor` read their rustc through it.

A preset is a module of the target spec (`lib/modules/target-spec.nix`), so it may set any option and users override any field with ordinary module priorities ([Write a preset](../../how-to/write-a-preset.md)). Target specs are resolved per (workspace, target): `targets.<triple>` and `workspaces.<ws>.targets.<triple>` are both kept as unevaluated modules, and `mkRepository` evaluates them together once per workspace that builds the triple (`breakbulk.evalTargetSpec`), with the module arguments `pkgs`, `name` (the triple) and `toolchain` (the workspace's). That evaluation runs twice: once to read [`preset`](../../reference/options/targets.md#targetsnamepreset) (its default follows the traits, which are options too), then again with the chosen preset imported, since a module's imports cannot depend on its options.

A built-in preset's definitions have fixed names, whatever the target: a choice between mechanisms (`windows` for msvc or MinGW) is a `lib.mkIf` on `config.traits`, and a check on the traits fails in the values. The module system reads every module's names before any option's value, so names that depended on an option would recurse. A preset applied to an attribute set binds its options (`presets.windows { inherit sdk; }`); applied by the module system, which passes `config`, it is the module.

So two workspaces on different Rust releases that build the same triple get the LLVM tools (`lib/llvm-versions.nix`) and wasi-sdk (`lib/wasi-sdk.nix`) of their own compiler, from one repository-wide preset. A workspace's own entry merges with the repository's as two definitions of the same options do; a target with neither a repository-wide entry nor any spec field in the workspace has no spec, as before.

The resolved spec is `repo.workspaces.<ws>.target.<triple>.spec`. A target whose preset needs no arguments gets it unless another preset is set, with or without an entry: when the `pkgs` given to `mkRepository` is a Linux package set, the native target gets `linux` (glibc) or `linuxStatic` (musl, e.g. `pkgs.pkgsMusl`), following `pkgs.stdenv.hostPlatform`, not the machine running the evaluation; another Linux `-gnu` target gets `linux`, a `-musl` one `linuxStatic`, a Windows `-gnu` or `-gnullvm` one `windows`, a component-linking WASI target (`wasm32-wasip2`) `wasmComponent`, and a UEFI target `uefi`. The choice is `presetRule { pkgs; triple; traits; }` in `lib/target-traits.nix` (`defaultPreset` gives its name). A triple whose preset needs arguments or a choice has none: msvc and macOS need an SDK, and wasm32 without WASI is either `wasmWeb` or `wasmComponent`. For such a triple `presetRule` names the presets, and the target fails at evaluation (`present` in `lib/repository.nix`) unless it sets a preset, a `linker`, or `preset = null`: with the build machine's linker, its empty spec would fail only at the first link. Any other triple (bare metal, Android, the BSDs) keeps an empty spec.

`preset = null` turns the default off. Every preset also sets the host spec from `pkgs.buildPackages`, so host units always get the build machine's tools.

Every preset takes its linker from one function, `chooseLinker` in `lib/presets/linker.nix` (["Linker selection"](../targets.md#linker-selection)): `linkerKind { triple; lto; flavor; kind; rustc; staticNonPie; }` names the kind (`lld`, `cc`, `mold`, `clang-lld`, `lld-link`, `wasm-ld`, `wasm-component-ld`, `mingw-lld`, `zig`), and `chooseLinker` builds that wrapper from the preset's package set and LLVM. The Linker column below is that function's result. On Linux the default follows rustc's own choice (`rustcPicksLld`): `lld` where rustc's target spec links with its bundled lld (linker flavor `gnu-lld-cc`), else `cc`. That depends on the rustc build, the build machine and the release, read from `toolchainFacts` (`version`, and `bundledLld`, false for nixpkgs' rustc) and checked against rustc's source and `--print target-spec-json`; [L11](../../reference/assumptions.md#l11-where-rustc-links-with-its-bundled-lld) has the table. `kind` is the target's `linkerKind`, which every preset takes like `traits`; `hostSpec` gives it to host units when the target is the build machine's triple. `lld` and `clang-lld` put nixpkgs' `ld.lld` behind bintools-wrapper's `ld-wrapper.sh` in the C compiler's bintools, so rpaths and `NIX_LDFLAGS` apply as with GNU ld.

The Runner column comes the same way from `chooseRunner` in `lib/presets/runner.nix`: `runnerKind { traits; canExecute; nativeBuilder; flavor; }` names the kind (`native`, `native-builder` with [`testSystem`](../../reference/options/targets.md#targetsnametestsystem), `qemu-user`, `wine` for x86\_64 and i686 Windows, `wasmtime` for WASI, `wasm-bindgen`, `ld-so` for zig, `none`), and test runs build with `runners.testPkgsFor { pkgs; testSystem; }`.

Preset env is added per unit by platform, never through Cargo's `[env]`.

Presets are named for what they are for, and each picks its mechanism from the target triple's traits: `linux`, `linuxStatic` (musl for a `-musl` triple, static-pie glibc for a `-gnu` one), `linuxPortable` (an old glibc, through zig), `windows` (msvc for `-msvc`, MinGW for `-gnu` and `-gnullvm`), `wasmWeb` and `wasmComponent` (componentized core modules for `wasm32-unknown-unknown`, rustc's own component linker for `wasm32-wasip2`). An option that does not apply to the triple's mechanism is ignored, so one bound preset can serve several targets (`windows { inherit sdk; }` for an msvc and a gnu triple). Debug handling is not part of a preset: it is the target's `debugInfo` (see [Source paths at run time](../../reference/unit-builder.md#source-paths-at-run-time)), `split` on Linux, `keep` elsewhere.

Static linking is one rule (`presetHelpers.staticLinking { traits; crtStatic; }`), used by `linuxStatic` (both mechanisms) and `windows` (`crtStatic`; default off for msvc, on for MinGW): `+crt-static` in the target rustflags, and, on an ELF target, where it makes the C library static too, `PKG_CONFIG_ALL_STATIC=1` in the target env. pkg-config-rs then passes `--static` to pkg-config (so `Libs.private` comes along) and prints `rustc-link-lib=static=…` for libraries with an archive in a non-system directory (pkg-config 0.3.34, `infer_static` and `is_static_available`; it has no rule of its own for musl).

Before, only the static glibc preset set it, so a musl product whose pkg-config library has a private dependency failed to link (`static-pkgconfig-musl-*` in `tests/presets/fixtures.nix`: `undefined symbol: bbbar_base` without it). On Windows `+crt-static` makes the C runtime static, but an .exe still loads DLLs, so pkg-config keeps its default there.

### Windows msvc

```nix
targets.x86_64-pc-windows-msvc.preset = breakbulk.presets.windows {
  sdk = breakbulk.xwinSdk {            # fixed-output; meta.license = unfree
    inherit pkgs;
    manifestVersion = 17; crt = "14.44.17.14"; sdk = "10.0.26100";
    arches = [ "x86_64" "aarch64" ];  # one download can serve both; the hash depends on the set
    channelManifest = null;           # optional: pin Microsoft's channel manifest too
    hash = "sha256-…";
  };
  crtStatic = true;
  extraSdks = [ ];                  # e.g. a driver kit, with its own include and lib dirs
};
```

The include directories are passed twice in different syntax: `-imsvc` for `clang-cl` and `-isystem` for bindgen's libclang. `aarch64-pc-windows-msvc` and `i686-pc-windows-msvc` use the same preset; the SDK's library directories are picked by the target's `xwinArch` trait (`sdk.libDirs.<xwinArch>`: `x86` for i686), and an SDK built without that arch fails naming `xwinSdk`'s `arches`. `RC`, `RCFLAGS`, `LIB` and `INCLUDE` have no target suffix, so the preset applies them to target units only.

`lld-link` records the path of rustc's randomly named temporary directory in the PDB, and the PDB's hash goes into the `.exe`, so links are not reproducible as is (`/Brepro` does not help). The preset's linker is a wrapper that copies those inputs to a fixed path before linking. Details are in [spikes/msvc.md](https://github.com/schlarpc/breakbulk/blob/spikes-archive/docs/spikes/msvc.md).

### wasm

- **wasm-bindgen version.** The `wasmBindgen` stage reads the `wasm-bindgen` version from the workspace's `Cargo.lock`. It picks the matching `wasm-bindgen-cli_<version>` from nixpkgs, or builds that version from crates.io with a hash from a table shipped with the library. If neither exists, evaluation fails naming the version.
- **Unwrapped clang.** C code uses clang from the LLVM matching rustc, never the stdenv compiler wrapper. A wrapped gcc can silently produce host objects for a wasm target.

### wasmComponent on wasip2

`-C link-self-contained=no` is the wrong switch on `wasm32-wasip2`: rustc's target spec lists `crt1-command.o` only among its self-contained objects (`rustc_target` `targets/wasm32_wasip2.rs`, `crt_objects.rs`), so turning self-contained linking off links executables without `_start` ("entry symbol not defined").

The preset leaves it on, so `libc.a`, the crt1 objects and `libunwind.a` all come from rustc's self-contained directory, and gives C code the headers of the same wasi-libc.

Rust's dist builds copy that directory's wasi-libc from `$WASI_SDK_PATH/share/wasi-sysroot` (bootstrap `wasi_libdir`, `copy_self_contained_objects`), with `WASI_SDK_PATH` pinned in `src/ci/docker/host-x86_64/dist-various-2/Dockerfile`: wasi-sdk 30 for Rust 1.95 and 1.96, 33 for 1.97 to 1.99, 34 for 1.100 to 1.102.

`lib/wasi-sdk.nix` maps the Rust release to that wasi-sdk release and fetches its sysroot asset from GitHub (fixed-output); each sysroot's `lib/wasm32-wasip2/libc.a` is byte-identical to the toolchain's self-contained one (checked for 1.95, 1.96, 1.97, 1.99, 1.100 beta and 1.101 nightly, and by the `wasip2-linker` check).

A Rust release outside the table fails evaluation with a message naming the file; `wasiSdkVersion` or `wasiSdk` (a sysroot path) override it. An earlier version put nixpkgs' wasi-libc ahead of rustc's directory and swapped the crt1 objects in the linker wrapper; that linked nixpkgs' wasi-libc (wasi-sdk 32) in place of the one Rust ships and tests std with (33). Products are components, installed by root kind: a command under `bin/`, a library component under `lib/`.

The wasmtime runner keeps its compilation cache in `$TMPDIR`.

### Windows MinGW (gnu, gnullvm)

GCC 15 and later passes `-pie` to the linker for every executable (its link spec `%{static|shared|r:;!no-pie:-pie}`). GNU ld reads it as `--dynamicbase` for PE; lld's MinGW driver rejects it, so the preset's `ld.lld` drops it (lld's MinGW driver uses `--dynamicbase` by default, and rustc passes it too). lld stamps PE headers with the current time unless told otherwise (`lld/MinGW/Driver.cpp`), hence `--no-insert-timestamp`. With these, the `.exe` link units of both triples pass `nix-build --check`. nixpkgs' mingw gcc keeps winpthreads outside the toolchain, and rustc's `+crt-static` link asks for `-l:libpthread.a`, hence the extra search path. aarch64 `-gnullvm` uses `pkgsCross.mingw-ucrt-aarch64`; its product and test binary link (ARM64 PE, time stamp 0, only system DLLs) and rebuild byte-identically, but nothing runs them: wine runs no ARM64 code.

### linuxPortable (zig)

`presets.linuxPortable { glibc ? "2.17"; systemLibraries ? [ ]; allowStorePaths ? [ ]; overlays ? [ ]; }` (`lib/presets/linux-portable.nix`) makes programs that run on any glibc Linux at least as new as `glibc`: everything Nix provides is linked statically, and only glibc's own libraries and `systemLibraries` are loaded at run time.

Three parts: the target's package set builds nixpkgs' libraries as static libraries against `glibc` (below); target units get `PKG_CONFIG_ALL_STATIC=1`, so pkg-config-rs links every library whose archive it finds statically, as for `linuxStatic`; every product gets the check `portableNoStorePaths`, `stageHelpers.noStorePaths { allow = allowStorePaths; }`, which fails on any Nix store path named in the product's files (a statically linked OpenSSL looks for its configuration in the OPENSSLDIR compiled into it, which nixpkgs' static build sets to a store path), and every product gets the check `portableLibraries`, `stageHelpers.neededLibraries { allowed = stageHelpers.glibcLibraries ++ stageHelpers.gccRuntimeLibraries ++ systemLibraries; }`, which reads the `NEEDED` entries of every ELF file in the product (`readelf -d`, as auditwheel reads a wheel's) and fails naming any other library.

`glibcLibraries` are the sonames of glibc's own libraries in the releases from 2.17 on (`libc.so.6`, `libm.so.6`, `libpthread.so.0`, `libdl.so.2`, `librt.so.1`, `libutil.so.1`, `libresolv.so.2`, `libnsl.so.1`, `libcrypt.so.1`, `libanl.so.1`, `libmvec.so.1`, …) and the loaders (`ld-linux-*.so.*`); `gccRuntimeLibraries` are `libgcc_s.so.1` and `libstdc++.so.6`, which manylinux's policy also allows and which `linuxPortable` allows by default for a C++ dependency built with g++; a zig-linked Rust program needs neither (zig links its own unwinder; checked: the fixture product needs `libc.so.6`, `ld-linux-x86-64.so.2`, `libpthread.so.0` and `libdl.so.2`).

`linux-portable-libraries-cxx` runs the preset's check on a g++-built program that needs both. There is no option to bundle libraries or set an rpath.

For an old glibc version: `zig cc -target <zigArch>-linux-gnu.<glibc>` wrappers (the target's `zigArch` trait) as linker, C and C++ compiler and archiver for target units. The host triple is the same, so host units keep the host linker through the planner's linker rewrite.

A separate derivation pre-warms zig's global cache for the target (an executable and a shared library linked with the libraries rustc passes). zig refuses a read-only cache (`manifest_create AccessDenied`, zig 0.17.0), but a copy at another path is a full hit: about 60 MB, copied in well under 0.1 s, against about 10 s to rebuild it.

The wrapper itself copies the cache into `$TMPDIR` on first use in a unit (copy aside, then rename, so parallel cc jobs do not race), so `breakbulk-unit` has no zig special case. The wrapper also drops the `--target=<Rust triple>` the cc crate passes, which zig cannot parse. The linker wrapper (`zigLinker` in `lib/presets/linker.nix`) links as GNU ld behind nixpkgs' cc-wrapper would, which the other linker kinds go through: it adds the `-L` directories of the env capture's `NIX_LDFLAGS`, and it turns rustc's `-Wl,-Bdynamic` into `-Wl,-search_paths_first`, because GNU ld's `-Bdynamic` takes an archive where a directory has no shared library and zig's does not (`lib_search_strategy = .no_fallback`, zig 0.17.0 `src/main.zig`). Without both, a library that another library's pkg-config file names without a path (libidn2's `Libs.private: -lunistring`, which pkg-config-rs passes as a plain `-l` because it finds no archive on the paths pkg-config printed) is not found. Test binaries name the FHS loader `/lib64/ld-linux-x86-64.so.2`, which a Nix sandbox lacks, so the runner starts them through the build machine's `ld.so`.

That proves the binaries run, not that they run on the old glibc, so an opt-in check (`nix run .#test-linux-portable-container`; `linux-portable-centos7-*` in `tests/presets/extra-targets.nix`, not in `nix flake check` because it downloads the image) also runs the product and the test binaries inside a real glibc 2.17 userland: CentOS 7.9's Docker Hub image, pulled by digest as a fixed-output derivation and unpacked into the store, used as the root of a `bwrap` container (a temporary overlay, with the store, `$TMPDIR`, `/tmp` and `$out` bound in), which works inside the Nix sandbox.

The binaries are executed directly, so CentOS's own loader and `libc.so.6` load them; a fixture test compares `gnu_get_libc_version()` with 2.17. Units are unchanged by the container runner; only test runs differ.

Native libraries from nixpkgs' own builds need nixpkgs' newer glibc and defeat the purpose. The preset's package set (`targets.<triple>.packageSet`, set with `mkDefault` like every preset's) is therefore nixpkgs cross-built for a static variant of the target platform, with `zig cc` for `glibc` as its compiler:

```nix
import pkgs.path {
  localSystem = pkgs.stdenv.buildPlatform;
  crossSystem = { config = "x86_64-none-linux-gnu"; isStatic = true; };
  crossOverlays = [ <breakbulk's> ] ++ overlays;
  config = pkgs.config // { replaceCrossStdenv = <the zig stdenv>; };
}
```

The platforms differ (`isStatic`), so nixpkgs uses its cross stdenv stages (`pkgs/stdenv/cross/default.nix`): tools come from `buildPackages`, nixpkgs' own native builds (`nativeBuildInputs`, a package's [`nativeInputs`](../../reference/options/packages.md#packagesnamenativeinputs)), and a library input from [`packages.<name>.inputs`](../../reference/options/packages.md#packagesnameinputs) gets its own library dependencies from the same set through splicing, so a library never links one built against a newer glibc. `isStatic` makes nixpkgs' packages build static libraries, as in pkgsStatic.

The platform's GNU triple has the vendor `none`, not the Rust triple's: for the build machine's own triple, the cross tools' prefix (`x86_64-unknown-linux-gnu-gcc`) is also the name of the build machine's unwrapped gcc, which a package's `depsBuildBuild` compiler puts first on `PATH` (bash's build failed linking with it), and configure scripts given the same `--build` and `--host` try to run their test programs.

The stdenv (`config.replaceCrossStdenv`) is nixpkgs' cc-wrapper around the preset's `zig cc` with no libc, so setup hooks, `NIX_CFLAGS_COMPILE` and pkg-config work as usual, with two of pkgsStatic's adapters, `makeStaticLibraries` (`--enable-static --disable-shared`, `BUILD_SHARED_LIBS=OFF`, meson's `default_library=static`) and `propagateBuildInputs` (static libraries need their dependencies at the final link). nixpkgs' own stdenv for a static glibc platform also has `makeStaticBinaries`, which links every program with `-static` against nixpkgs' `glibc.static`; zig cannot link glibc statically ("libc of the specified target requires dynamic linking"), and it would be a newer glibc. Test phases are off.

nixpkgs counts the build machine as able to run the platform's programs (`canExecute` ignores the libc and `isStatic`), so meson (no exe wrapper) and CMake (`CMAKE_CROSSCOMPILING_EMULATOR=env`, `pkgs/build-support/lib/cmake.nix`) run the programs they link. zig links the FHS loader, which the sandbox lacks, so the stdenv's compiler links executables with the build machine's loader (`--dynamic-linker`, in the wrapper's `cc-ldflags`, which it passes only when linking). Archives have no loader, and products are linked by the target units' own `zig cc`, never by this one.

breakbulk's overlay, before the preset's `overlays` (nixpkgs overlays applied to the set's own packages, its `crossOverlays`):

- `bash`, `bashNonInteractive` (libcurl's `curl-config` names it): `-std=c23`. bash builds its helper programs with the build machine's gcc, whose default C standard (C23 from gcc 15) its configure script assumes the target's compiler has too; nixpkgs passes `-std=c23` only when the compiler is clang, which this one does not claim to be (below), and the build fails (`'bool' cannot be defined via 'typedef'`).
- `libiconv`: nixpkgs' is glibc's `iconv.h`, copied from a glibc built for the platform, which `zig cc` cannot build; zig's glibc headers and stubs have iconv, so it is empty.
- `libev`: its `static` argument (default `isStatic`) links its programs with `-static`; it is `false`, and the library is static either way.
- `libpsl` (libcurl's): libpsl compiles in two paths of the list, both in nixpkgs' `publicsuffix-list` (`portableNoStorePaths` found them in the fixture's product): the one `psl_latest()` reads (`--with-psl-distfile`, `-DPSL_DISTFILE`) and the one the built-in list was made from, which `psl_latest()` and `psl_builtin_outdated()` also read (`--with-psl-file`, written into `suffixes_dafsa.h` as `_psl_filename` by `src/psl-make-dafsa`; libpsl 0.21.5). Both become `/usr/share/publicsuffix/public_suffix_list.dat`, where Debian and Fedora install the list; the built-in list is still made from nixpkgs'.
- `openssl`: built with `OPENSSLDIR=/etc/ssl` (so `ENGINESDIR` is `/etc/ssl/engines-3`, nixpkgs' static layout) and `MODULESDIR=/usr/lib/ossl-modules`, as make variables of its build phase only, since OpenSSL compiles them in from make variables (`-DOPENSSLDIR="\"$(OPENSSLDIR)\""`, OpenSSL 3.5.9 `Configurations/unix-Makefile.tmpl`) while `make install` still installs into the store. Without it, nixpkgs' static OpenSSL names its `etc` output (`OPENSSLDIR`, `ENGINESDIR`) and, after `remove-references-to`, `/nix/store/eeee…-openssl-3.5.9/lib/ossl-modules` (`MODULESDIR`), and `portableNoStorePaths` fails on the fixture's product naming all of them (checked by hand).

Other packages that name nixpkgs' `glibc` directly, take `isStatic` to mean fully static programs, or apply a fix only when `stdenv.cc.isClang`, need an overlay entry of the same kind; the `portableLibraries` and `portableNoStorePaths` checks find what slips through.

The wrapped compiler must not claim to be clang: for clang, cc-wrapper adds nixpkgs gcc's libstdc++ and passes arguments in a response file with backslash-escaped commas, which zig keeps, silently dropping `-Wl,-soname,…` and `-Wl,-rpath,…` (zig 0.17.0). Nothing in the set is in a binary cache: libcurl with its libraries (18 packages, OpenSSL and zlib among them) took about 25 minutes with 2 jobs on a 4-core machine that other builds were loading.

The set is a second nixpkgs evaluation, which every workspace with the target makes, since its target units' base env capture uses the set's stdenv (host units' captures come from the set's `buildPackages`, whose derivations are nixpkgs' own). Measured on the `linux-portable` fixture, which has no library inputs: evaluating its `portableLibraries` check goes from 1.43 to 2.27 million thunks and from 438 to 661 MiB allocated, about one more second of CPU.

Limits: C++ libraries would use zig's libc++, not nixpkgs' libstdc++.

The `linux-portable-native-glibc` check builds OpenSSL, zlib and libcurl with its libraries this way for `openssl-sys`, `libz-sys` and `curl-sys` and checks that they are archives only, that the product has nixpkgs' libcurl (built with nghttp2; curl-sys's fallback is its bundled curl), needs GLIBC\_2.17 at most and loads none of them, `linux-portable-native-libraries` runs the product's `portableLibraries` check and `linux-portable-native-no-store-paths` its `portableNoStorePaths` (OpenSSL's directories are `/etc/ssl`…); `stages-no-store-paths` shows `noStorePaths` failing on a store path in binary bytes, in a text file and with a scrubbed hash, and passing once they are allowed; `linux-portable-libraries-negative` shows the check failing, naming the library, when only `libc.so.6` is allowed; `linux-portable-native-centos7-*` (in `nix run .#test-linux-portable-container`) runs the product and tests in the CentOS 7 container.

### build-std

A nightly toolchain with `rust-src` and `[unstable] build-std = [...]` in the project's config. Cargo resolves the standard library's own workspace (`<sysroot>/lib/rustlib/src/rust/library`, with its own `Cargo.lock`) with the project's source configuration, even for `core` only (cargo `src/compiler/standard_lib.rs`, `resolve_std`), so its crates.io dependencies (`hashbrown`, `libc`, `rustc-literal-escaper`, …) must be in the offline planner's vendor directory too. They need no fetching: `rust-src` ships them vendored with `.cargo-checksum.json` (`library/vendor`, the directory source that `library/.cargo/config.toml` names).

- When the project's config files set `unstable.build-std`, the planner links a merged crates.io directory in its scratch directory: the project's vendored crates, plus every `library/vendor` crate whose name and version the project does not have, and points crates.io's replacement at it with one more `--config` file (`crates/breakbulk-plan/src/build_std.rs`).
- `cargo metadata` of the standard library's workspace (`--all-features`, since `build-std-features` may turn on any optional dependency) is merged into the planner's metadata, so stubs find their package (`compiler_builtins` and `object` have build scripts) and the rewriter knows the packages.
- Paths of the standard library's packages and of its vendored crates are toolchain store paths. They stay literals, like the sysroot, instead of becoming `crateSrc` references; the toolchain is an input of every unit anyway. A unit's working directory can therefore be a literal toolchain path (`cwd` is a reference or a literal in the plan format).
- `-Z` flags (`-Zforce-unstable-if-unmarked`, `-Zembed-metadata=no`) are Cargo's own, in argv as traced. Remapping is Cargo's (trim-paths, on 1.101 and later): `<library>/core=/cargo/deps/core-0.0.0` and the sysroot's `/rustc/<commit>`.
- Tested by `build-std` (`x86_64-unknown-none`, `core` and `compiler_builtins`, no preset: rustc's own linker) and `build-std-deps` (the host triple with `build-std = ["std"]` and the linux preset; `std`'s `hashbrown`, `libc`, `addr2line`, … are planned from `library/vendor`, built, and the program runs) in `tests/presets/build-std.nix`. `build-std-tests` instantiates both fixtures' test plans.

### Apple targets

One preset, `presets.darwin` (`lib/presets/darwin.nix`), for both kinds of build machine; the build machine picks the toolchain. Written once for both: `-C split-debuginfo=packed`, the deployment target, the `adhocSign` stage (after `install`) and the runner choice (none, or a Mac builder with `nativeBuilder`). Only the Linux route exists; a Mac build machine fails at evaluation naming [#13](https://github.com/schlarpc/breakbulk/issues/13), where nixpkgs' Darwin stdenv (its cc wrapper and the `darwinSdkVersion` SDK) will take the linker rule's other branch.

**The SDK** (`lib/apple-sdk.nix`). On a machine that is not a Mac, `sdk` is required, and evaluation without it fails naming Apple's "Xcode and Apple SDKs Agreement", which authorizes the SDK only on Apple-branded computers (§2.2.A, §2.5, §2.7). `breakbulk.appleSdk { pkgs; version; }` is nixpkgs' fixed-output fetch (`pkgs/by-name/ap/apple-sdk/common/fetch-sdk.nix`, at a version `metadata/versions.json` pins), the same store path nixpkgs' `apple-sdk` builds from, with `meta.license` unfree (nixpkgs sets none), so a package set must admit it. The SDK table lists what each SDK version asks of its linker, one row per requirement from the first version that has it: 27.0's `.tbd` stub files list `arm64e.x1-macos` targets, which an LLD before 23.1.3 rejects ("could not load TAPI file … unknown target").

**The linker** (`lib/presets/linker.nix`). The rule for an Apple target is keyed on the build machine (`rustc.host`). From Linux there is no C driver to link through: nixpkgs has no Linux-to-Darwin cross C toolchain (`pkgsCross.aarch64-darwin.stdenv.cc` does not evaluate on `x86_64-linux`: `cctools` is not available on a Linux host platform). rustc runs the linker itself with its `darwin` lld flavor (`-flavor darwin`), chosen by the linker's name: `rust-lld` or `lld`; rustc infers nothing from `ld64.lld` (rustc_target `spec/mod.rs`, `infer_linker_hints`). It passes the SDK it reads from `SDKROOT` as `-syslibroot` (rustc_codegen_ssa `back/link.rs`, `add_apple_sdk`), and the deployment target as `-platform_version`. The kind is the toolchain's own `rust-lld` when it ships one (`bundledLld`: rustup, rust-overlay and fenix do), found on the PATH rustc gives the linker, because its LLVM is rustc's, which `-C linker-plugin-lto` needs; else `ld64.lld`, nixpkgs' lld of rustc's LLVM major (nixpkgs' rustc ships no `rust-lld`). `linkerKind` forces either. The linker's side of the SDK table is `linkerFeatures`: the LLD release with each feature, or the nixpkgs patch that backports it (nixpkgs' LLVM 18 to 22 carry `backport-minimal-arm64e_x1-support.patch`). When the linker lacks what the SDK needs, the preset fails at evaluation, naming the SDK, the requirement, the linker's LLD version (`toolchainFacts.llvmVersion`, from `rustc -vV` for a rust-lang toolchain) and the ways out: an older SDK, a newer toolchain, `linkerKind`. It never switches kinds on its own, which would trade a clear error for an LLVM mismatch. lld's Mach-O writer zeroes object modification times in the debug map by default (`zeroModTime`), and gives the output a content-derived UUID and, on arm64, an ad hoc signature.

**C code.** Unwrapped clang from rustc's LLVM release, with `--target=<triple> -isysroot <SDK>` in `CFLAGS_<triple>` and bindgen's arguments. cc-rs gives `-isysroot` itself only for Xcode's clang or targets other than macOS (cc 1.11, `add_default_flags`), and adds the deployment target.

**Deployment target.** Every target unit gets `MACOSX_DEPLOYMENT_TARGET`, which rustc, cc-rs, clang, CMake and autotools all read, so C built by any of them targets the macOS release the Rust code links for. `deploymentTarget` sets it in the target's `env`. Without it, the preset sets the target's `stdenv` to the build machine's with a `preHook` that runs `rustc --print deployment-target --target <triple>` and exports the value, so the target's env captures record it and every target unit replays it (layer 2). rustc prints `MACOSX_DEPLOYMENT_TARGET=<version>`: the variable's value when it is set (raised to rustc's minimum, with a warning), else its own default (checked with rustc 1.99.1: `11.0` for `aarch64-apple-darwin`, `10.12` for `x86_64-apple-darwin`). Reading it at build time keeps rustc's table in rustc. Your own `targets.<triple>.stdenv` replaces the preset's, and with it this default; set `deploymentTarget` then. Without the workspace's `rustc` (a preset called directly), the variable stays unset, as rustc and cc-rs default to the same value. `llvm-ar` archives.

**Debug information.** A linked Mach-O file has no DWARF of its own: lld writes a debug map (stab entries naming each object file), and dsymutil gathers the DWARF into a `<file>.dSYM` bundle. rustc runs `dsymutil` from `PATH` after the link when `-C split-debuginfo` is `packed`, the Apple target specs' own default (rustc_codegen_ssa `back/link.rs`, `link_natively`); Cargo passes `unpacked` on Apple targets whenever debuginfo is on (cargo `core/profiles.rs`), which leaves the DWARF in the build directory's objects. The preset's rustflag `-C split-debuginfo=packed` comes after Cargo's, so it wins, also over a profile's own `unpacked`, whose DWARF would stay in object files the sandboxed unit discards; the planner reads the last one ([Target facts from rustc](planner.md#target-facts-from-rustc)), so the linking unit gets a `debug` output, and the unit builder moves the `.dSYM` directory into it. `PATH` also has `rust-objcopy` (LLVM's `llvm-objcopy`), which rustc runs for `-C strip` on Apple targets and which nixpkgs' rustc does not ship. `debugInfo` defaults to `split` on Apple targets: `splitDebug` puts the `.dSYM` next to where its file lands in the `debug` output (`bin/app.dSYM`, `lib/libx.dylib.dSYM`), checks that it has the file's UUID, and removes the debug map with `llvm-strip -S`. `strip` removes it as well, and drops the `.dSYM`.

**Signing.** `llvm-strip` signs a signed file again with the name of the file it writes as the identifier, so a stage that writes under a temporary name puts that name in the signature. `adhocSign` signs every executable, dylib and bundle with `rcodesign`, which keeps an existing identifier unless told otherwise, with the file's own name (or `identifiers.<name>`), after `install`.

`zig cc` links a program that needs only `libSystem` with no SDK (zig's own stub file), but it ships no frameworks and ignores the deployment target rustc passes; it is not used.
