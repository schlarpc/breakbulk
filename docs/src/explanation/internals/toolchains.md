# Target traits and presets

## Target traits

Every decision that depends on the target platform reads one record, the target's **traits**, made by one function (`breakbulk.targetTraits.resolve`, `lib/target-traits.nix`). No other code inspects how a triple is spelled. This follows the linker choice (`lib/presets/linker.nix`): a decision is a function of facts, and the facts have one home.

- **Base fields** are what rustc's own cfg says about the target: `vendor`, `os`, `env`, `abi` and `families` (`target_vendor`, `target_os`, `target_env`, `target_abi`, `target_family`), plus `arch`, the triple's first component as spelled (`i686`, `armv7`, `riscv64gc`; tool and SDK names use that spelling, not `target_arch`). `parse` reads them from a built-in target name. The check `target-traits-rustc` compares it with `rustc --print cfg --target <t>` for every built-in target of nixpkgs' rustc: 248 of 321 are known, all agreeing (the abi only where the name spells one; rustc infers powerpc64's `elfv1`/`elfv2`). The rest (RTOSes such as nuttx, vxworks, qnx; `.json` target specs) return null.
- **Derived fields** follow from the base fields: `kernel` (`linux` for `linux` and `android`, `darwin` on Apple, the OS for other OSes with their own kernel, null for bare metal, UEFI, wasm and CUDA) for kernel-level facts; `isLinux` (a Linux userland: os `linux`, so not Android, Android targets have no linker rule and fail at evaluation naming issue #27 until an NDK preset exists), `isWindows`, `isMsvc`, `isMingw` (Windows with env `gnu`, so `-gnullvm` too), `isApple`, `isWasm`, `isWasi`, `isBareMetal`, `isUefi`; `objectFormat` (`elf`, `pe`, `macho`, `wasm`); `executableSuffix`, `sharedLibraryPrefix`/`sharedLibrarySuffix`, `staticLibraryPrefix`/`staticLibrarySuffix`, rustc's target-spec `exe_suffix`, `dll_prefix`/`dll_suffix` (dylib and cdylib) and `staticlib_prefix`/`staticlib_suffix`, which `target-traits-rustc` compares with `rustc --print file-names --crate-type <t>` for every built-in target it knows (all 248 agree; a crate type rustc drops for a target is skipped); `debugArtifacts`, the debuginfo files a link writes that `--print file-names` does not name, as a list of `{ suffix; when; perObject ? false; directory ? false; }`: msvc and UEFI `[ { suffix = ".pdb"; when = "always"; } ]` (rustc links both with an MSVC-style linker, UEFI with rust-lld as lld-link, which writes it for every linked crate whatever `-C debuginfo` says), ELF `[ { suffix = ".dwp"; when = "split-packed"; } { suffix = ".dwo"; when = "split-unpacked"; perObject = true; } ]`, Apple `[ { suffix = ".dSYM"; when = "split-packed"; directory = true; } ]` (unverified, no Darwin builders), else none; `dylibPathVar` and `dylibPathSep` (Cargo's `dylib_path_envvar` for a process running natively on the target: `PATH` on Windows, `DYLD_FALLBACK_LIBRARY_PATH` on Apple, `LD_LIBRARY_PATH` elsewhere, null for wasm and bare metal); `debugInfo` (the default of `targets.<t>.debugInfo`, `split` on a Linux ELF target, `keep` elsewhere).
- **Who reads them:** the linker kind (`linkerKind`), the test runner kind (`runnerKind`) and the test process's dynamic-library variable (`testRuns.dylibPathOf`), static linking (`staticLinking`), the default debug handling and so the debug stage, remap scope and build ID (`lib/products.nix`), the install layout (`install`, `splitDebug`'s placement of side files) and binary names (`executableSuffix`), and instantiation's `debug` output rule (`debugArtifacts`). The Rust programs never parse a triple: `breakbulk-instantiate` receives the part it needs in `toolchains.json` (`targetTraits`, from `targetTraits.forRust`; breakbulk-format `TargetTraits`), so plans and `units.json` are unchanged.
- **Bring your own target.** `targets.<triple>.traits` (and `workspaces.<ws>.targets.<triple>.traits`) is an attribute set merged over the built-in traits: base fields recompute the derived ones, and derived fields set there win. A name that is not a trait is an evaluation error listing the known ones. A triple with no built-in traits (a custom target, a `.json` spec) needs at least the base fields:

  ```nix
  targets."thumbv7em-myboard-none" = {
    traits = { os = "none"; abi = "eabihf"; };
    linker = "${myToolchain}/bin/arm-none-eabi-gcc";
  };
  ```

  Without them, reading any trait of that target fails with a message naming `targets."<triple>".traits`. A custom triple also has no nixpkgs package set of its own (`presets.targetPkgsFor` imports nixpkgs with `crossSystem.config = <triple>`, which nixpkgs may not parse): give `targets.<triple>.packageSet` when its packages have library inputs. The failure is lazy: a target whose traits nothing reads (one with an explicit linker and no default stages) still works. The resolved record is `repo.workspaces.<ws>.target.<triple>.traits`; presets receive it as `traits` (every `breakbulk.presets.*` takes it, as it takes `toolchain`), and a preset called directly uses the triple's built-in traits.

## Toolchain presets

The LLVM version matching rustc comes from `rustc.llvmPackages` only for nixpkgs' own rustc; rust-overlay and fenix toolchains do not carry it. The library ships a table from Rust version to LLVM major version, overridable per toolchain (`llvmMajor`, `llvmPackages`). The table is the fast path; for a rustc it does not cover (older than its first release, newer than the last release checked, or without a version), a tiny derivation reads the major from `rustc -vV`, through import-from-derivation. Every fact about a toolchain comes from one function, `breakbulk.toolchainFacts.of { pkgs; rustc; }` (`lib/toolchain-facts.nix`): `version`, `majorMinor`, `llvmMajor`, `wasiSdkVersion` and `capabilities` (see [Toolchain capabilities](planner.md#toolchain-capabilities)), each from the toolchain's attributes and breakbulk's tables when they can say, else from one `rustc -vV` probe (release and LLVM major), so the wasi-sdk choice now also works for a rustc without a `version` attribute. `llvmVersions.packagesFor` and `wasiSdk.sysrootFor` read their rustc through it.

A preset is a function from `{ pkgs, triple, …options }` to a `targets.<triple>` module, so users override any field with ordinary module priorities. Target specs are resolved per (workspace, target): `targets.<triple>` and `workspaces.<ws>.targets.<triple>` are both kept as unevaluated modules, and `mkRepository` evaluates them together once per workspace that builds the triple (`lib/modules/target-spec.nix`), passing the workspace's toolchain. A preset applied through `preset` receives it as `toolchain` (every `breakbulk.presets.*` advertises that argument; a plain user function that does not is called without it) and uses its `rustc` unless the preset was given `rustc`, `llvmMajor` or `llvmPackages` itself. So two workspaces on different Rust releases that build the same triple get the LLVM tools (`lib/llvm-versions.nix`) and wasi-sdk (`lib/wasi-sdk.nix`) of their own compiler, from one repository-wide preset. A workspace's own entry merges with the repository's as two definitions of the same options do; a target with neither a repository-wide entry nor any spec field in the workspace has no spec, as before. The resolved spec is `repo.workspaces.<ws>.target.<triple>.spec`. When the `pkgs` given to `mkRepository` is a Linux package set, the native target gets `linux` (glibc) or `linuxStatic` (musl, e.g. `pkgs.pkgsMusl`) unless another preset is set; the choice is `nativeDefaultPreset` in `lib/target-traits.nix` and follows `pkgs.stdenv.hostPlatform`, not the machine running the evaluation. Another preset is set either through `targets.<native>.preset` or by defining the target directly from a preset (every preset's value carries an internal marker for this); `preset = null` turns it off. Every preset also sets the host spec from `pkgs.buildPackages`, so host units always get the build machine's tools. Every preset takes its linker from one function, `chooseLinker` in `lib/presets/linker.nix` (design.md "Linker selection"): `linkerKind { triple; lto; flavor; }` names the kind (`mold`, `clang-lld`, `lld-link`, `wasm-ld`, `wasm-component-ld`, `mingw-lld`, `zig`), and `chooseLinker` builds that wrapper from the preset's package set and LLVM. The Linker column below is that function's result. The Runner column comes the same way from `chooseRunner` in `lib/presets/runner.nix`: `runnerKind { traits; canExecute; nativeBuilder; flavor; }` names the kind (`native`, `native-builder` with `testSystem`, `qemu-user`, `wine` for x86\_64 and i686 Windows, `wasmtime` for WASI, `wasm-bindgen`, `ld-so` for zig, `none`), and test runs build with `runners.testPkgsFor { pkgs; testSystem; }`. Preset env is added per unit by platform, never through Cargo's `[env]`.

Presets are named for what they are for, and each picks its mechanism from the target triple's traits: `linux`, `linuxStatic` (musl for a `-musl` triple, static-pie glibc for a `-gnu` one), `linuxPortable` (an old glibc, through zig), `windows` (msvc for `-msvc`, MinGW for `-gnu` and `-gnullvm`), `wasmWeb` and `wasmComponent` (componentized core modules for `wasm32-unknown-unknown`, rustc's own component linker for `wasm32-wasip2`). An option that does not apply to the triple's mechanism is ignored, so one bound preset can serve several targets (`windows { inherit sdk; }` for an msvc and a gnu triple). Debug handling is not part of a preset: it is the target's `debugInfo` (see [Source paths at run time](../../reference/unit-builder.md#source-paths-at-run-time)), `split` on Linux, `keep` elsewhere.

Static linking is one rule (`presets.staticLinking { traits; crtStatic; }`), used by `linuxStatic` (both mechanisms) and `windows` (`crtStatic`; default off for msvc, on for MinGW): `+crt-static` in the target rustflags, and, on an ELF target, where it makes the C library static too, `PKG_CONFIG_ALL_STATIC=1` in the target env. pkg-config-rs then passes `--static` to pkg-config (so `Libs.private` comes along) and prints `rustc-link-lib=static=…` for libraries with an archive in a non-system directory (pkg-config 0.3.34, `infer_static` and `is_static_available`; it has no rule of its own for musl). Before, only the static glibc preset set it, so a musl product whose pkg-config library has a private dependency failed to link (`static-pkgconfig-musl-*` in `tests/presets/fixtures.nix`: `undefined symbol: bbbar_base` without it). On Windows `+crt-static` makes the C runtime static, but an .exe still loads DLLs, so pkg-config keeps its default there.

### Windows msvc

```nix
targets.x86_64-pc-windows-msvc.preset = breakbulk.presets.windows {
  sdk = breakbulk.xwinSdk {            # fixed-output; meta.license = unfree
    inherit pkgs;
    manifestVersion = 17; crt = "14.44.17.14"; sdk = "10.0.26100";
    arches = [ "x86_64" "aarch64" ];  # one download can serve both; the hash depends on the set
    channelManifest = null;           # optional: pin Microsoft's channel manifest too
    hash = "sha256-…";
  };
  crtStatic = true;
  extraSdks = [ ];                  # e.g. a driver kit, with its own include and lib dirs
};
```

The include directories are passed twice in different syntax: `-imsvc` for `clang-cl` and `-isystem` for bindgen's libclang. `aarch64-pc-windows-msvc` uses the same preset; the SDK's library directories are picked by the triple's arch (`sdk.libDirs.<arch>`). `RC`, `RCFLAGS`, `LIB` and `INCLUDE` have no target suffix, so the preset applies them to target units only.

`lld-link` records the path of rustc's randomly named temporary directory in the PDB, and the PDB's hash goes into the `.exe`, so links are not reproducible as is (`/Brepro` does not help). The preset's linker is a wrapper that copies those inputs to a fixed path before linking. Details are in [spikes/msvc.md](https://github.com/schlarpc/breakbulk/blob/spikes-archive/docs/spikes/msvc.md).

### wasm

- **wasm-bindgen version.** The `bindgen` stage reads the `wasm-bindgen` version from the workspace's `Cargo.lock`. It picks the matching `wasm-bindgen-cli_<version>` from nixpkgs, or builds that version from crates.io with a hash from a table shipped with the library. If neither exists, evaluation fails naming the version.
- **Unwrapped clang.** C code uses clang from the LLVM matching rustc, never the stdenv compiler wrapper. A wrapped gcc can silently produce host objects for a wasm target.

### wasmComponent on wasip2

`-C link-self-contained=no` is the wrong switch on `wasm32-wasip2`: rustc's target spec lists `crt1-command.o` only among its self-contained objects (`rustc_target` `targets/wasm32_wasip2.rs`, `crt_objects.rs`), so turning self-contained linking off links executables without `_start` ("entry symbol not defined"). The preset leaves it on, so `libc.a`, the crt1 objects and `libunwind.a` all come from rustc's self-contained directory, and gives C code the headers of the same wasi-libc. Rust's dist builds copy that directory's wasi-libc from `$WASI_SDK_PATH/share/wasi-sysroot` (bootstrap `wasi_libdir`, `copy_self_contained_objects`), with `WASI_SDK_PATH` pinned in `src/ci/docker/host-x86_64/dist-various-2/Dockerfile`: wasi-sdk 30 for Rust 1.95 and 1.96, 33 for 1.97 to 1.99, 34 for 1.100 to 1.102. `lib/wasi-sdk.nix` maps the Rust release to that wasi-sdk release and fetches its sysroot asset from GitHub (fixed-output); each sysroot's `lib/wasm32-wasip2/libc.a` is byte-identical to the toolchain's self-contained one (checked for 1.95, 1.96, 1.97, 1.99, 1.100 beta and 1.101 nightly, and by the `wasip2-linker` check). A Rust release outside the table fails evaluation with a message naming the file; `wasiSdkVersion` or `wasiSdk` (a sysroot path) override it. An earlier version put nixpkgs' wasi-libc ahead of rustc's directory and swapped the crt1 objects in the linker wrapper; that linked nixpkgs' wasi-libc (wasi-sdk 32) in place of the one Rust ships and tests std with (33). Products are components, installed under `pkg/` like every wasm product. The wasmtime runner keeps its compilation cache in `$TMPDIR`.

### Windows MinGW (gnu, gnullvm)

GCC 15 and later passes `-pie` to the linker for every executable (its link spec `%{static|shared|r:;!no-pie:-pie}`). GNU ld reads it as `--dynamicbase` for PE; lld's MinGW driver rejects it, so the preset's `ld.lld` drops it (lld's MinGW driver uses `--dynamicbase` by default, and rustc passes it too). lld stamps PE headers with the current time unless told otherwise (`lld/MinGW/Driver.cpp`), hence `--no-insert-timestamp`. With these, the `.exe` link units of both triples pass `nix-build --check`. nixpkgs' mingw gcc keeps winpthreads outside the toolchain, and rustc's `+crt-static` link asks for `-l:libpthread.a`, hence the extra search path. aarch64 `-gnullvm` maps to `pkgsCross.ucrtAarch64` but is untested.

### linuxPortable (zig)

`presets.linuxPortable { glibc ? "2.17"; systemLibraries ? [ ]; allowStorePaths ? [ ]; backend ? "zig"; rebuildInputs ? [ ]; rebuildOverrides ? { }; }` (`lib/presets/linux-portable.nix`) makes programs that run on any glibc Linux at least as new as `glibc`: everything Nix provides is linked statically, and only glibc's own libraries and `systemLibraries` are loaded at run time. Three parts: `rebuildInputs` are rebuilt as static libraries only (below); target units get `PKG_CONFIG_ALL_STATIC=1`, so pkg-config-rs links every library whose archive it finds statically, as for `linuxStatic`; every product gets the check `portableNoStorePaths`, `stageHelpers.noStorePaths { allow = allowStorePaths; }`, which fails on any Nix store path named in the product's files (a statically linked OpenSSL looks for its configuration in the OPENSSLDIR compiled into it, which nixpkgs' static build sets to a store path), and every product gets the check `portableLibraries`, `stageHelpers.neededLibraries { allowed = stageHelpers.glibcLibraries ++ stageHelpers.gccRuntimeLibraries ++ systemLibraries; }`, which reads the `NEEDED` entries of every ELF file in the product (`readelf -d`, as auditwheel reads a wheel's) and fails naming any other library. `glibcLibraries` are the sonames of glibc's own libraries in the releases from 2.17 on (`libc.so.6`, `libm.so.6`, `libpthread.so.0`, `libdl.so.2`, `librt.so.1`, `libutil.so.1`, `libresolv.so.2`, `libnsl.so.1`, `libcrypt.so.1`, `libanl.so.1`, `libmvec.so.1`, …) and the loaders (`ld-linux-*.so.*`); `gccRuntimeLibraries` are `libgcc_s.so.1` and `libstdc++.so.6`, which manylinux's policy also allows and which `linuxPortable` allows by default for a C++ dependency built with g++; a zig-linked Rust program needs neither (zig links its own unwinder; checked: the fixture product needs `libc.so.6`, `ld-linux-x86-64.so.2`, `libpthread.so.0` and `libdl.so.2`). `linux-portable-libraries-cxx` runs the preset's check on a g++-built program that needs both. There is no option to bundle libraries or set an rpath. `backend = "zig"` is the only backend.

For an old glibc version: `zig cc -target <arch>-linux-gnu.<glibc>` wrappers as linker, C and C++ compiler and archiver for target units. The host triple is the same, so host units keep the host linker through the planner's linker rewrite. A separate derivation pre-warms zig's global cache for the target (an executable and a shared library linked with the libraries rustc passes). zig refuses a read-only cache (`manifest_create AccessDenied`, zig 0.17.0), but a copy at another path is a full hit: about 60 MB, copied in well under 0.1 s, against about 10 s to rebuild it. The wrapper itself copies the cache into `$TMPDIR` on first use in a unit (copy aside, then rename, so parallel cc jobs do not race), so `breakbulk-unit` has no zig special case. The wrapper also drops the `--target=<Rust triple>` the cc crate passes, which zig cannot parse. Test binaries name the FHS loader `/lib64/ld-linux-x86-64.so.2`, which a Nix sandbox lacks, so the runner starts them through the build machine's `ld.so`. That proves the binaries run, not that they run on the old glibc, so an opt-in check (`nix run .#test-linux-portable-container`; `linux-portable-centos7-*` in `tests/presets/extra-targets.nix`, not in `nix flake check` because it downloads the image) also runs the product and the test binaries inside a real glibc 2.17 userland: CentOS 7.9's Docker Hub image, pulled by digest as a fixed-output derivation and unpacked into the store, used as the root of a `bwrap` container (a temporary overlay, with the store, `$TMPDIR`, `/tmp` and `$out` bound in), which works inside the Nix sandbox. The binaries are executed directly, so CentOS's own loader and `libc.so.6` load them; a fixture test compares `gnu_get_libc_version()` with 2.17. Units are unchanged by the container runner; only test runs differ.

Native libraries from `packages.<name>.inputs` are nixpkgs builds against nixpkgs' newer glibc and defeat the purpose. The preset's package set therefore wraps nixpkgs: a package input that reads any derivation from it gets an evaluation warning naming the package, unless it is listed in the opt-in `rebuildInputs` (`presets.linuxPortable { rebuildInputs = [ "openssl" "zlib" ]; }`). Each listed package is `pkgs.<name>.override { stdenv = makeStaticLibraries zigStdenv; }` (nixpkgs' stdenv adapter that pkgsStatic uses: `--enable-static --disable-shared`, `BUILD_SHARED_LIBS=OFF`, meson's `default_library=static`), with `static = true`, `shared = false`, `enableStatic = true` and `enableShared = false` for whichever of those arguments the package takes (OpenSSL's `static` gives `no-shared`; zlib's `shared`), with the other listed packages passed for the arguments it takes, and with its test phases off (their test programs ask for the FHS loader). A rebuild that still installs a shared library (`*.so`, `*.so.*` in any output) fails, naming the file. A rebuild whose compiled-in paths would name the store is changed per package (`rebuildOverrides.<name> = old: { … }`, applied with `overrideAttrs` after the rest, replacing breakbulk's entry for that package; `null` drops it): OpenSSL is built with `OPENSSLDIR=/etc/ssl` (so `ENGINESDIR` is `/etc/ssl/engines-3`, nixpkgs' static layout) and `MODULESDIR=/usr/lib/ossl-modules`, as make variables of its build phase only, since OpenSSL compiles them in from make variables (`-DOPENSSLDIR="\"$(OPENSSLDIR)\""`, OpenSSL 3.5.9 `Configurations/unix-Makefile.tmpl`) while `make install` still installs into the store. Without it, nixpkgs' static OpenSSL names its `etc` output (`OPENSSLDIR`, `ENGINESDIR`) and, after `remove-references-to`, `/nix/store/eeee…-openssl-3.5.9/lib/ossl-modules` (`MODULESDIR`), and `portableNoStorePaths` fails on the fixture's product naming all of them (checked by hand). `zigStdenv` is nixpkgs' cc-wrapper around the preset's `zig cc` with no libc, so setup hooks, `NIX_CFLAGS_COMPILE` and pkg-config work as usual. The wrapped compiler must not claim to be clang: for clang, cc-wrapper adds nixpkgs gcc's libstdc++ and passes arguments in a response file with backslash-escaped commas, which zig keeps, silently dropping `-Wl,-soname,…` and `-Wl,-rpath,…` (zig 0.17.0). Tools (`nativeInputs`) come from `buildPackages` and are unaffected. Measured on 4 cores: zlib about 10 s, OpenSSL about 5 minutes; neither is in a binary cache. Limits: only libraries whose library dependencies are listed too (or have none) are correct, because unlisted ones still come from nixpkgs (and, being shared libraries, fail `portableLibraries`); C++ libraries would use zig's libc++, not nixpkgs' libstdc++. The `linux-portable-native-glibc` check builds OpenSSL and zlib this way for `openssl-sys` and `libz-sys` and checks that both are archives only, that the product needs GLIBC\_2.17 at most and loads neither, `linux-portable-native-libraries` runs the product's `portableLibraries` check and `linux-portable-native-no-store-paths` its `portableNoStorePaths` (OpenSSL's directories are `/etc/ssl`…); `stages-no-store-paths` shows `noStorePaths` failing on a store path in binary bytes, in a text file and with a scrubbed hash, and passing once they are allowed; `linux-portable-libraries-negative` shows the check failing, naming the library, when only `libc.so.6` is allowed; `linux-portable-native-centos7-*` (in `nix run .#test-linux-portable-container`) runs the product and tests in the CentOS 7 container.

### build-std

A nightly toolchain with `rust-src` and `[unstable] build-std = [...]` in the project's config. Cargo resolves the standard library's own workspace (`<sysroot>/lib/rustlib/src/rust/library`, with its own `Cargo.lock`) with the project's source configuration, even for `core` only (cargo `src/compiler/standard_lib.rs`, `resolve_std`), so its crates.io dependencies (`hashbrown`, `libc`, `rustc-literal-escaper`, …) must be in the offline planner's vendor directory too. They need no fetching: `rust-src` ships them vendored with `.cargo-checksum.json` (`library/vendor`, the directory source that `library/.cargo/config.toml` names).

- When the project's config files set `unstable.build-std`, the planner links a merged crates.io directory in its scratch directory: the project's vendored crates, plus every `library/vendor` crate whose name and version the project does not have, and points crates.io's replacement at it with one more `--config` file (`crates/breakbulk-plan/src/build_std.rs`).
- `cargo metadata` of the standard library's workspace (`--all-features`, since `build-std-features` may turn on any optional dependency) is merged into the planner's metadata, so stubs find their package (`compiler_builtins` and `object` have build scripts) and the rewriter knows the packages.
- Paths of the standard library's packages and of its vendored crates are toolchain store paths. They stay literals, like the sysroot, instead of becoming `crateSrc` references; the toolchain is an input of every unit anyway. A unit's working directory can therefore be a literal toolchain path (`cwd` is a reference or a literal in the plan format).
- `-Z` flags (`-Zforce-unstable-if-unmarked`, `-Zembed-metadata=no`) are Cargo's own, in argv as traced. Remapping is Cargo's (trim-paths, on 1.101 and later): `<library>/core=/cargo/deps/core-0.0.0` and the sysroot's `/rustc/<commit>`.
- Tested by `build-std` (`x86_64-unknown-none`, `core` and `compiler_builtins`, no preset: rustc's own linker) and `build-std-deps` (the host triple with `build-std = ["std"]` and the linux preset; `std`'s `hashbrown`, `libc`, `addr2line`, … are planned from `library/vendor`, built, and the program runs) in `tests/presets/build-std.nix`.

### Darwin (not started, [#13](https://github.com/schlarpc/breakbulk/issues/13))

There are no Mac builders here. What it would take: the planner and units must run on `aarch64-darwin` (the Nix sandbox on macOS is weaker, so the determinism check matters more); the linker is the nixpkgs Darwin cc wrapper (ld64, or lld for cross-language LTO) with the SDK from nixpkgs' `apple-sdk`; products need the Darwin stages already listed in design.md (`dsymutil`, `strip`, ad-hoc code signing, which must come last since it hashes the binary); split debug info is `.dSYM` bundles, not `.debug` files; and `-C split-debuginfo` defaults differ (`unpacked` on macOS), which changes what the linking unit must capture. Cross-building to Darwin from Linux is out of scope (SDK licensing); tests need a native builder (`testSystem`).
