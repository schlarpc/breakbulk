# The Nix library

Everything users configure goes through one `lib.evalModules` call; the rest of the library turns the evaluated configuration into derivations. This page covers the library's structure, a few cross-cutting behaviors (curated `-sys` defaults, feature matrices), and how the dev shell matches the planner's Cargo invocation.

The library is one `lib.evalModules` call over user modules, plus functions that turn the evaluated config into derivations. A flake-parts module wraps it for flake users; its `root` defaults to the flake's `self`, which flake-parts passes to every top-level module as a special argument (`tests/flake-self/run.sh` checks it gives the same derivations as `root = ./.`).

- `env` values may reference any derivation, including another workspace's products: `env.UI_DIST = repo.workspaces.ui.target.wasm32-unknown-unknown.packages.ui;`. They are passed to instantiation by reference.
- Curated defaults for common `-sys` crates ship with the library (`lib/sys-defaults.nix`): native inputs only, never a switch that swaps a bundled C library for a system one (the removed ones are listed there). They are `sysDefaults.packages.<name>`, by crate name, defined at `mkDefault` priority so a plain definition replaces one; each is a module whose `package` argument is the lockfile entry, so version-dependent settings are a condition in the module. `layersFor` in `lib/repository.nix` puts them first among a package's settings layers, and `hostOnly` in `lib/package-settings.nix` keeps only their host side on a target without a package set.
- Package settings are one set of options (`lib/modules/package-settings.nix`) and every layer is a module of them: `sysDefaults.packages.<name>`, `sysDefaults.dependents.<name>`'s result, `workspaces.<ws>.memberDefaults`, `packages.<name>`, and each one's `target.<triple>`, `variant.<v>` and `variant.<v>.target.<triple>`. `layersFor` in `lib/repository.nix` lists, for one lockfile entry, the curated defaults, the curated dependents' layers and the workspace's `memberDefaults` (path packages only) and `packages.<name>`. `evaluate` in `lib/package-settings.nix` evaluates them as one module set, each through `layer` (`lib/modules/types.nix`) at a rank in [0, 1), the entry as the `package` argument; the `target` and `variant` options keep each module with the rank of the layer that gave it (`subLayers`), and `on { triple; variant; }` extends the evaluation with those for the triple and variant, each ranked between its layer and the next. An entry without any layer has no evaluation; one evaluation per entry is shared by the triples and variants that add no sub-layer. Every reader (unit env and env captures, test runs, products, `extraSources`, `sources`, the dev shell) reads the evaluated settings. Each mkWorkspace call is one workspace, triple and variant, and builds its own source views, so a variant layer's `extraSources`, `test.sourceScope` and `sources` cost no more evaluation than a triple's. A unit's env is the merged top level plus `forHost` or `forTarget` by the unit's side.
- A `packages` key that names no crate in any lockfile is an evaluation warning, not silence.
- Feature matrices are sets of variants made by one generator, `breakbulk.variants.featurePowerset`, which returns a workspace module (`workspaces.<ws>.imports`; a workspace definition is a full module for that). `scope = "workspace"` combines one feature list for the whole workspace, with `--no-default-features`; `scope = "package"` makes cargo-hack's per-package runs (`--feature-powerset` or `--each-feature`, `depth`, exclusions; each run a variant with `packages = [ <pkg> ]`, as cargo-hack runs each package on its own), from each member's `[features]` and optional dependencies in `workspaces.<ws>.members`. Being a module, it adds definitions beside the user's instead of building attribute sets they would have to merge by hand. Its variants have `checks.products` and `checks.tests` false at `lib.mkDefault`, so a matrix's products, test runs and doctests stay out of `repo.checks` until asked for; hand-written variants (a coverage variant included) default to both `true`. A check variant's `check` is in `repo.checks` either way (`checks.check`). Tools are presets of the same kind: `breakbulk.variants.clippy` and `breakbulk.variants.coverage` are workspace modules over the general variant options (`mode`, `rustflags`, `rustcWorkspaceWrapper`, `wrapperEnv`, `wrapperConfig`) and `memberDefaults.variant.<v>`; a variant's `mode` is only the Cargo command (`build` or `check`), and each plan's command is a row of `lib/cargo-commands.nix`.
- A variant's settings on one target come from extending the variant's own module evaluation (`extendModules`) with the target's `variantDefaults` and the variant's `target.<triple>` layer. The variant's definitions keep their priorities that way, so a later layer merges with them by module rules instead of meeting already-merged values. Each added layer goes through `layer` (`lib/modules/types.nix`), which lowers the priority number of its single-valued definitions by its rank (-0.5 for the workspace's `variantDefaults`, imported into the variant's own evaluation, and -0.25 for the target's, so it raises it, under the variant's own definitions at rank 0; 0.5 for `target.<triple>`), inside attribute sets and submodules too, mkIf, mkMerge, mkOverride, function modules and imported files included; so the higher layer wins at equal priority, any two integer priorities keep their order, and lists keep their priority, so they still concatenate, ordered by rank (`mkOrder`). Package layers go through the same `layer`. Every per-variant decision in `lib/repository.nix` (plan flags, outputs, `repo.checks`) reads these per-target settings, and their assertions are checked per target. No layer rewrites what it adds: `variantDefaults.features` reach every variant as written, and Cargo rejects a feature that no `-p` package accepts (a user's function module can choose with `acceptsFeature`, `lib/manifest.nix`). So `featurePowerset` defines only what each run needs (its `features`, `packages`, and `noDefaultFeatures = true` or `allFeatures = true`) as plain definitions, and other definitions of them merge as for any variant.

## Dev shell

The planner always passes `--target`, and local Cargo without it behaves differently: rustflags reach build scripts, every unit's `-C metadata` changes, and outputs move. The dev shell therefore:

- is set up for one target, [`devShell.target`](../../reference/options/workspaces.md#workspacesnamedevshelltarget), by default the workspace's [`defaultTarget`](../../reference/options/workspaces.md#workspacesnamedefaulttarget): the native triple when the workspace targets it, else its only target, else the project's `build.target` when that is one triple among the targets, else none (#32).

  `defaultTarget` also picks what the `packages`, `tests` and `testRuns` shortcuts (and the flake-parts module's `packages`) name; every target is built either way.

  `build.target` comes from the planner's own config reader (`ProjectConfig::read`: the project's `.cargo/config.toml` files from the workspace directory up, with `include`s and Cargo's merging, never `$CARGO_HOME` or the environment, as for every Cargo setting breakbulk reads), through `breakbulk-plan --build-target-only` (`mkBuildTarget`, an import-from-derivation made only when the earlier rules do not decide and the workspace has a config file; setting `defaultTarget` skips it).

  A triple that is not one of the workspace's targets is an evaluation error. With none, the shell exports no target and no spec, so the project's own `build.target` (or Cargo's host default) applies locally;
- exports `CARGO_BUILD_TARGET=<target>`;
- exports that target's toolchain spec as Cargo env config (`CARGO_TARGET_<TRIPLE>_LINKER`, and `CARGO_TARGET_<TRIPLE>_RUSTFLAGS` or `CARGO_BUILD_RUSTFLAGS`, whichever key the planner chose), matching the planner's `--config`. A small derivation (`breakbulk-plan --cargo-env-only`) computes it by the planner's own rule from the project's Cargo config files and `rustc --print cfg`, without running Cargo, so the shell still opens when planning fails, for example on a broken `Cargo.toml`. It is read by import-from-derivation;
- exports `CARGO_PROFILE_<P>_TRIM_PATHS=all` when the planner turns trim-paths on, for each profile `P` of the default variant's build and test plans (`profile` and `testProfile`, see [trim-paths](planner.md#trim-paths)): trim-paths is part of the profile Cargo hashes into `-C metadata`. The same `--cargo-env-only` derivation decides it, by the planner's own rule from the workspace root's `Cargo.toml` and the config files read as TOML and the toolchain's [`trimPaths`](../../reference/options/workspaces.md#workspacesnametoolchainfactscapabilitiestrimpaths) capability, without a plan, so the shell opens with a broken manifest on every Cargo version; a file that does not parse is a warning and counts as not setting trim-paths;
- includes the union of the packages' native env captures, because one shell cannot scope env per unit (a union is only valid within one platform, so a cross target's own `inputs`, libraries for that platform, are left out; its `nativeInputs` and `env` are included);
- merges package env in `Cargo.lock` order, then the target's `env`, then the Cargo env config above, then [`devShell.env`](../../reference/options/workspaces.md#workspacesnamedevshellenv), where `null` removes a variable and its derivation from the shell's inputs. A variable that packages set to different values is a warning, unless the Cargo env config or `devShell.env` sets it;
- warns about `CARGO_*` variables in the user's environment that the planner will not see.

Limits, documented: binaries move to `target/<triple>/…`; a missing input declaration can work locally and fail in Nix; and for same-triple presets (static glibc, zig) local Cargo cannot keep target env away from host build scripts.
