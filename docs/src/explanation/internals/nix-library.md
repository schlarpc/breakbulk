# The Nix library

Everything users configure goes through one `lib.evalModules` call; the rest of the library turns the evaluated configuration into derivations. This page covers the library's structure, a few cross-cutting behaviors (curated `-sys` defaults, feature matrices), and how the dev shell matches the planner's Cargo invocation.

The library is one `lib.evalModules` call over user modules, plus functions that turn the evaluated config into derivations. A flake-parts module wraps it for flake users; its `root` defaults to the flake's `self`, which flake-parts passes to every top-level module as a special argument (`tests/flake-self/run.sh` checks it gives the same derivations as `root = ./.`).

- `env` values may reference any derivation, including another workspace's products: `env.UI_DIST = repo.workspaces.ui.target.wasm32-unknown-unknown.packages.ui;`. They are passed to instantiation by reference.
- Curated defaults for common `-sys` crates ship with the library (`lib/sys-defaults.nix`): native inputs only, never a switch that swaps a bundled C library for a system one (the removed ones are listed there). They are `sysDefaults.packages.<name>`, by crate name, defined at `mkDefault` priority so a plain definition replaces one; each is a function of the lockfile entry, so version-dependent settings need no `name@<req>` key. `layersFor` in `lib/repository.nix` puts them first among a package's settings layers, and keeps only their host side on a target without a package set.
- Package settings are one shape (`lib/modules/package-settings.nix`) used in several places: `sysDefaults.packages.<name>`'s result, `workspaces.<ws>.memberDefaults`, `packages.<name>`, and each one's `target.<triple>`, `variant.<v>` and `variant.<v>.target.<triple>`. `layersFor` lists, for one lockfile entry in the plans of one variant on one triple, the curated defaults, the workspace's `memberDefaults` (path packages only) and each matching `packages` key, each followed by those layers of its own; every reader (unit env and env captures, test runs, products, `extraSources`) folds that one list. Each mkWorkspace call is one workspace, triple and variant, and builds its own source views, so a variant layer's `extraSources` and `test.sourceScope` cost no more evaluation than a triple's. A unit's env is the merged top level plus `forHost` or `forTarget` by the unit's side.
- An override whose `version` or name matches nothing in any lockfile is an evaluation warning, not silence.
- Feature matrices are sets of variants made by helpers: `breakbulk.variants.featurePowerset` (one feature list for the whole workspace, with `--no-default-features`) and `breakbulk.variants.packageFeaturePowerset` (cargo-hack's per-package runs: `--feature-powerset` or `--each-feature`, `depth`, exclusions; each run a variant with `packages = [ <pkg> ]`, as cargo-hack runs each package on its own)). Their variants have `checks = false` unless the arguments set it, so a matrix's products, test runs and doctests stay out of `repo.checks` until asked for; hand-written variants (a coverage variant included) default to `checks = true`. A check or clippy variant's `check` is in `repo.checks` either way.
- A variant's settings on one target come from extending the variant's own module evaluation (`extendModules`) with the target's `variantDefaults` and the variant's `target.<triple>` layer. The variant's definitions keep their priorities that way, so a later layer merges with them by ordinary module rules instead of meeting already-merged values. Every per-variant decision in `lib/repository.nix` (plan flags, outputs, `repo.checks`) reads these per-target settings, and their assertions are checked per target. `packageFeaturePowerset` gives each run's feature settings priority 90, between a plain definition and `mkForce`: `variantDefaults` name workspace features, which Cargo rejects for a `-p <pkg>` run whose package does not have them (`Workspace::collect_matching_features` accepts only the selected packages' own features and `<dep>/<feat>` of their dependencies).

## Dev shell

The planner always passes `--target`, and local Cargo without it behaves differently: rustflags reach build scripts, every unit's `-C metadata` changes, and outputs move. The dev shell therefore:

- is set up for one target, [`devShell.target`](../../reference/options/workspaces.md#workspacesnamedevshelltarget), by default the workspace's [`defaultTarget`](../../reference/options/workspaces.md#workspacesnamedefaulttarget): the native triple when the workspace targets it, else its only target, else the project's `build.target` when that is one triple among the targets, else none (#32).

  `defaultTarget` also picks what the `packages`, `tests` and `testRuns` shortcuts (and the flake-parts module's `packages`) name; every target is built either way.

  `build.target` comes from the planner's own config reader (`ProjectConfig::read`: the project's `.cargo/config.toml` files from the workspace directory up, with `include`s and Cargo's merging, never `$CARGO_HOME` or the environment, as for every Cargo setting breakbulk reads), through `breakbulk-plan --build-target-only` (`mkBuildTarget`, an import-from-derivation made only when the earlier rules do not decide and the workspace has a config file; setting `defaultTarget` skips it).

  A triple that is not one of the workspace's targets is an evaluation error. With none, the shell exports no target and no spec, so the project's own `build.target` (or Cargo's host default) applies locally;
- exports `CARGO_BUILD_TARGET=<target>`;
- exports that target's toolchain spec as Cargo env config (`CARGO_TARGET_<TRIPLE>_LINKER`, and `CARGO_TARGET_<TRIPLE>_RUSTFLAGS` or `CARGO_BUILD_RUSTFLAGS`, whichever key the planner chose), matching the planner's `--config`. A small derivation (`breakbulk-plan --cargo-env-only`) computes it by the planner's own rule from the project's Cargo config files and `rustc --print cfg`, without running Cargo, so the shell still opens when planning fails, for example on a broken `Cargo.toml`. It is read by import-from-derivation;
- exports `CARGO_PROFILE_<P>_TRIM_PATHS=all` when the planner turns trim-paths on for the default variant's profile `P` (see [trim-paths](planner.md#trim-paths)): trim-paths is part of the profile Cargo hashes into `-C metadata`. The same `--cargo-env-only` derivation decides it, by the planner's own rule from the workspace root's `Cargo.toml` and the config files read as TOML and the toolchain's [`trimPaths`](../../reference/options/workspaces.md#workspacesnametoolchaincapabilitiestrimpaths) capability, without a plan, so the shell opens with a broken manifest on every Cargo version; a file that does not parse is a warning and counts as not setting trim-paths;
- includes the union of the packages' native env captures, because one shell cannot scope env per unit (a union is only valid within one platform, so a cross target's own `inputs`, libraries for that platform, are left out; its `nativeInputs` and `env` are included);
- merges package env in `Cargo.lock` order, then the target's `env`, then the Cargo env config above, then [`devShell.env`](../../reference/options/workspaces.md#workspacesnamedevshellenv), where `null` removes a variable and its derivation from the shell's inputs. A variable that packages set to different values is a warning, unless the Cargo env config or `devShell.env` sets it;
- warns about `CARGO_*` variables in the user's environment that the planner will not see.

Limits, documented: binaries move to `target/<triple>/…`; a missing input declaration can work locally and fail in Nix; and for same-triple presets (static glibc, zig) local Cargo cannot keep target env away from host build scripts.
