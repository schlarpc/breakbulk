# Instantiation

Instantiation turns `plan.json` into one derivation per unit, and each root into a small wrapper derivation. It is pure templating, shared by both delivery modes, so IFD mode and dynamic-derivation mode produce the same unit derivations and the same root shape. This page covers its inputs, the shape of each unit derivation, the root shape, the two modes, and how root names are fixed before Cargo runs.

`breakbulk-instantiate` turns `plan.json` plus a source map into unit derivations. It does no compiling, fetching or source serialization. The same templating code serves both delivery modes, so both produce identical unit derivation paths.

## Inputs

- `plan.json`: the output of a plan derivation.
- `sources.json`: the names of workspace source views (keyed by directory relative to the repository root) and crate sources (keyed by package id).
- `toolchains.json`: the host and target specs, and the toolchain's capabilities. Tool store paths are passed as plain strings, so that literal store paths in the plan (rustc in `program`) can be matched to a tool by prefix.
- `overrides.json`: per-package env and env-capture names, keyed `name@version` or `name`.
- `outer.json`: what the wrappers are named after, and the output name of each predicted root's, each predicted doctest's and the docs' wrapper ([The root shape](#the-root-shape)).

In IFD mode, nothing with string context reaches instantiation. `units.json` names every path it needs (`{"unit": id, "output": o}`, `{"input": key}`) and the Nix side fills in the values with their context. This has two consequences: the output must contain zero store references, because `builtins.fromJSON` refuses strings with context; and a source edit or an override change does not rerun instantiation at all, only a plan change or an added or removed input does. Dynamic-derivation mode runs the same instantiation, then does the Nix side's substitution itself (see [Dynamic-derivation mode](#dynamic-derivation-mode)). Unit tests check that both substitutions give identical text and inputs; `nix run .#test-dynamic` checks identical `.drv` paths on Nix master.
- The predicted root list.

Instantiation therefore realises nothing except the plan and the source views. Neither the toolchain, nor crate sources, nor embedded products are built before units are known.

## Derivation shape per unit

| Field | Value |
| --- | --- |
| `name` | `<crate>-<version>-<kind>`, for example `ring-0.17.14-lib` or `ring-0.17.14-build-run` |
| `builder` | `breakbulk-unit`, with no arguments: the rendered value's `kind` says what it does |
| `env.BREAKBULK_UNIT` | Canonical JSON of the unit with every reference rendered |
| `outputs` | Library: `rmeta`, `rlib`. Bin or test: `out`. Build-script run: `out`, `flags`. Target-platform linking units (bins, tests, examples, cdylibs, dylibs, staticlibs) also `debug`, last, for their debuginfo side files, when the traced command makes rustc write them; so do target-platform libraries with an `rlib` output, for the per-object ones only (`.dwo` with `-C split-debuginfo=unpacked`, which rustc writes beside every object it compiles). One function decides both (`CompileUnit::has_debug_output`). Nix outputs are fixed before the build, so one function decides it from the argv and the plan's `targetDebuginfo`, which the planner read from its rustc's target spec (breakbulk-format `writes_debuginfo_side_files`, used by instantiation in both modes; see [Target facts from rustc](planner.md#target-facts-from-rustc)): the unit gets one when any of its `artifacts` applies. An artifact with `when = "always"` (the `.pdb` of msvc and UEFI) applies to every crate the linker produces (`bin`, `cdylib`, `dylib`, `--test`), because rustc passes `/DEBUG` to the MSVC-style linker whatever `-C debuginfo` and `-C strip` say (rustc_codegen_ssa `back/linker.rs`, `MsvcLinker::debuginfo`); one with `when = "split-packed"` or `"split-unpacked"` (ELF's `.dwp` and `.dwo`) when the effective `-C split-debuginfo` (the last one given, else the target's `splitDefault`) is that value and debuginfo is on (the last `-C debuginfo` or `-g` wins, as in rustc's `select_debuginfo`). A target whose spec lists none (wasm) never gets one. Input-addressed |
| `inputs` | `Built{drv, output}` for each referenced unit output, crate source, toolchain component and env capture; `Opaque` for each source view |
| `system` | The builder platform: the planner's system for compile units |

Referenced outputs are input-addressed or fixed-output, so their paths are known and rendered literally. The one exception is a product referenced through a package override in dynamic-derivation mode: products are resolved at build time there, so the reference is a placeholder and the referencing unit is resolved at build time too. So is every unit downstream of it, and each such reference is a placeholder as well ([spike B](https://github.com/schlarpc/breakbulk/blob/spikes-archive/docs/spikes/B-delivery.md)).

## The root shape

Everything after a root (test runs, test apps, doctests, a product's `linked` stage, the `buildScriptPaths` check) reads the root at build time, in both modes, so each has one implementation. A root is a wrapper derivation named `<outer name>-<package>.<kind>.<target>` (`crates/breakbulk-instantiate/src/shape.rs`). In dynamic-derivation mode the outer derivation submits it as its output `<package>.<kind>.<target>.drv`; Nix requires a submitted output to be named after the outer derivation, and IFD mode names it the same way.

Its output is a directory: `root`, a symlink to the root unit's output (for a test binary Cargo did not build, to its stub's, which succeeds); `not-built`, the reason, for a root Cargo did not build (a product root then has no `root` and does not depend on its stub, which is not written); `debug`, the unit's debuginfo side files and those of the libraries below a product root; and `breakbulk-root.json`, which says whether the plan has the root (or why not) and, for a test binary, what its test run and test app need from the plan (runtime `CARGO_*` env, the project's `[env]` variables Cargo set on it, the `flags` of its `rustc-env` runs, the `flags` of every run of its platform for the dynamic-library path, the package's directory, and nextest's synthesized metadata), with real paths that are all inputs of the wrapper. For a product root it lists the `flags` of the target-platform runs below it (`buildScriptFlags`).

Each predicted doctest gets the plan's doctest derivation with the package's test configuration (`BREAKBULK_TEST_RUNNERS`, `_ARGS`, `_ENV`, `_POST_RUN`, as `testRuns.doctestConfig` gives them; their values are input values, keyed `doctest:<package>:<attribute>`), and a wrapper `<outer name>-<package>.doctest` linking its output as `root`, or with `not-built` when the plan has no doctest for the package. A doctest in the plan that was not predicted is an error. Doctests are predicted from the manifests as `cargo test` selects them: the lib target of each selected member with `doctest` on and a `lib`, `rlib` or `proc-macro` crate type. A doc plan's docs derivation (always one, so its output can be named before planning) gets a wrapper `<outer name>-docs` linking its output as `root`. Two more wrappers list every unit output of the plan (`units.drv`) and the `flags` output of every build-script run (`runs.drv`).

On the evaluation side (`rootShape` in `lib/instantiate.nix`), each root is a small derivation that symlinks the wrapper's `root` and carries `breakbulkRoot`: the predicted `package`, `target`, `kind`, `test`, `platform` and `requiredFeatures`, and `wrapper`, the wrapper's output path. A product root Cargo did not build fails with the reason. `doctests.<pkg>` links the doctest wrapper's `root`, or, for a predicted doctest the plan lacks, logs why; `docs` links the docs wrapper's `root`; `allUnits` the `units.drv` wrapper; `buildScriptRuns.runsFile` the `runs.drv` wrapper's list.

What is therefore not known at evaluation time, in either mode:

- **Roots Cargo did not build** (required features) cannot be told apart from built ones. Building such a product root fails with the reason, and a product's `linked` stage leaves the root out at build time. When no root is left, `linked` holds only the no-binaries marker (`breakbulk-no-binaries`, listing the reasons), and every stage and check, guarded by the stage machinery, copies the marker to its outputs instead of running (see [Stage ordering](products.md#stage-ordering)). So `repo.checks` has the full product and its checks, and they succeed when Cargo built nothing. A skipped test binary's test run succeeds and writes the reason.
- **Test runs** read what they need from the wrapper's `breakbulk-root.json` at build time, through a small derivation per run that copies it out, narrowed to the run (`runInfo` in `lib/test-runs.nix`; [Tests](products.md#tests)), so that the run does not depend on the wrapper. With `test.runner = "nextest"` they write nextest's metadata from the wrapper's (`TestSpec.nextest`, with the sysroot library directory filled in at build time). `test_spec` in `breakbulk-instantiate` (`src/test_spec.rs`) computes a test binary's spec; `lib/test-runs.nix` adds only what the Nix side knows (the sysroot library directory, the target's dynamic-library variable) and does not read `plan.json`.
- **Test apps** read the wrapper's `breakbulk-root.json` when they run. The app script depends on the wrapper, so in dynamic-derivation mode it is resolved at build time, and its program path is a placeholder at evaluation time; `nix run` with `ca-derivations` builds it and substitutes the real path (`resolveString` in Nix's `src/nix/app.cc`). Every predicted test binary has an app; one Cargo did not build fails with the reason.

The cost is one small derivation per root more than linking the unit's output directly, and IFD mode imports `units.json` to name each wrapper. IFD mode also gives `rootUnits` (each root's unit output), `doctestDrvs` and `docsDrv`, for tests and debugging.

## IFD mode

The instantiate derivation runs `breakbulk-instantiate --emit json` and writes `units.json`, mapping each unit to its complete derivation attributes, and with `--outer` the root shape: the wrappers by output name, and the stubs, doctests and docs they link (`nodes`, which a reference names as it names a unit). The Nix side imports it and applies `derivation` to each entry. Nix computes output paths. A unit's attribute names do not depend on its substituted values: `passAsFile` is always there, naming `BREAKBULK_UNIT` when that is long and empty otherwise. So selecting one unit's output does not evaluate the values of any unit, and a package's `env` can name a product of the same plan.

## Dynamic-derivation mode

One outer derivation per plan (`lib/dynamic.nix`) is content-addressed with text-hashed outputs and requires the system feature `builder-rpc-v0`, which Nix advertises automatically when `dynamic-derivations` is enabled (Nix master since 2026-07-21; first release 2.36). Nix's own error names the missing feature. It is named `<ws>-<triple>-<variant>` for the build plan and `<ws>-<triple>-<variant>-test` for the test plan, because submitted outputs must be named `<outer name>-<output>` and that name appears in store paths. It has one output per predicted root, `<package>.<kind>.<target>.drv` (the root name with `/` as `.`), one per predicted doctest in the test plan, `<package>.doctest.drv`, plus `units.drv` and `runs.drv` ([The root shape](#the-root-shape)). The bench plan, when there is one, is `<ws>-<triple>-<variant>-bench`; the doc plan is `<ws>-<triple>-<variant>-doc`, with `docs.drv` for its docs derivation.

Its builder is `breakbulk-drv`, a separate binary (`crates/breakbulk-drv/`), so that harmonia and tokio do not reach `breakbulk-instantiate`, which IFD mode builds before evaluation can continue. `lib/tools.nix` builds each breakbulk binary with a `Cargo.lock` trimmed to its own dependencies, so a harmonia update does not change `breakbulk-unit` and so every unit. It uses `breakbulk-instantiate` as a library:

1. It runs the same instantiation as IFD mode over the same `sources.json`, `toolchains.json`, `overrides.json`, `roots.json` and `outer.json` (with `leave` or `submit`, below), giving the same `units.json` structure and root shape in memory.
   Before substituting, it makes the package views that [source prediction](sources.md#source-prediction) narrows, from their specs (`predict.json`): each tree is added as a `source` store path, the one IFD mode copies with `builtins.path`, and becomes its key's value. The views it narrows are inputs of the outer derivation.
2. It substitutes every reference as `lib/instantiate.nix` does, from `values.json`: every input key's value without context, plus its string context as `builtins.getContext` gives it. From those contexts and the unit references it computes each derivation's input derivations and input sources exactly as `derivation` would (a plain path becomes an input source, an output an input derivation; `drvPath` strings with "all outputs" context are rejected). Every unit gets `passAsFile` as in IFD mode: `BREAKBULK_UNIT` above the same length, empty below it.
3. It writes units, root stubs and wrappers in topological order with harmonia (pinned git commit) over the restricted daemon socket in `$NIX_REMOTE`, one connection for the whole build: output paths from harmonia's `hashDerivationModulo` (input `.drv` files it wrote are kept in memory, because the builder cannot read back what it added; the others are read from the store), the ATerm added as a text-hashed object whose references are its input sources and input derivations. `nix derivation add` cannot be used: paths added during the build are not visible inside its sandbox, and it reads its inputs. Every output variable must be present (as an empty string) before hashing. A derivation with a content-addressed or deferred input stays deferred, and its dependents reference its outputs by placeholder.
4. It submits each wrapper of the root shape with `SubmitOutput` as its output. The doctests' configuration values come in `values.json`, so changing them reruns the outer derivation.

The outer derivation's inputs are the plan, `breakbulk-drv`, the files above, and every `.drv` that a value's context names, as a plain path: the builder needs those `.drv` files to hash the units, but nothing is built before it runs except the plan. It prints one `breakbulk-drv: wrote <unit> <.drv path>` line per derivation; the dynamic-mode test compares them with IFD mode's.

A build plan has a second outer derivation when packages it can contain declare [`productInputs`](../configuration.md#products-as-inputs): their settings use products of this plan, so the outer derivation that makes those products must not take them. The second writes the declaring packages and every package that depends on one of them in `Cargo.lock` (by name, over every kind of dependency); call these the second's packages. The first, `<ws>-<triple>-<variant>`, gets no value of theirs (`lib/workspace.nix` `valueOwner` says which package's settings an input key holds) and leaves their units out (`outer.json` `leave`; a unit of another package that depends on one is an error). The second, `<ws>-<triple>-<variant>-product-users`, gets every value and writes every unit, since it cannot read the first's `.drv` files, so the units of both are the same `.drv` files. It submits only its packages' roots (`outer.json` `submit`), and its `units.drv` is `ws.allUnits.build`. Each root reads its wrapper from the outer derivation that submits it. The declarations are checked against `Cargo.lock` before planning: a declared product whose package is among the second's packages is an error that names the chain of dependencies.

On the evaluation side, each wrapper of the root shape is `builtins.outputOf <outer>."<output>".outPath "out"`. Unit derivations (`ws.units`) are not available; reading them is an error. Check variants, which have no roots, build their plans through `units.drv` (`ws.allUnits.<kind>`), as in IFD mode. `explainSharing` reads the units through IFD mode (`ifdUnits`: importing `units.json`, which builds `breakbulk-instantiate` and the plans): they are the same derivations, except downstream of an embedded product, where it describes IFD mode's.

The spike result is in [spikes/B-delivery.md](https://github.com/schlarpc/breakbulk/blob/spikes-archive/docs/spikes/B-delivery.md).
- `recursive-nix` is not used. It has an open removal proposal, and `builder-rpc-v0` replaces it for this purpose.

## Mode selection

`mode` defaults to `"dynamic"` when `builtins ? outputOf` (the builtin is only registered when the `dynamic-derivations` feature is enabled) and `builtins.compareVersions builtins.nixVersion "2.36pre" >= 0` (master reports `2.36.0pre…`, which compares below `"2.36"`), and to `"ifd"` otherwise (`lib/nix-features.nix`, `defaultMode`). Determinate Nix reports its upstream base version there, so the same check works for it. `ca` defaults to `mode == "dynamic"`.

Setting `mode` overrides the default; `mode = "dynamic"` on an evaluator without the `outputOf` builtin is an evaluation error. `repo.config.mode` is the mode chosen, and [`repo.nixFeatures`](../../reference/outputs.md#nixfeatures) the Nix features it needs. Every use of `outputOf`, of content addressing and of import from derivation goes through a gate in `lib/nix-features.nix` that checks it against that record. A daemon or builder older than the evaluator still fails with Nix's own error; the docs point to `mode = "ifd"`.

The daemon needs `dynamic-derivations` too: a daemon without it refuses to store the outer derivation ("text-hashed derivation output") even when the evaluator has it. mkRepository passes the mode to each workspace instance as `delivery`, with the record as `nixFeatures`.

Unit derivations are identical in both modes. Products are not (resolved at build time in dynamic-derivation mode, input-addressed in IFD mode), so teams that mix Nix versions should pin the mode to share product cache entries.

## Root names are fixed at evaluation time

Nix attribute names, and a dynamic derivation's outputs, must be known at evaluation time, but the roots are discovered by the planner. The Nix library predicts them from the manifests with `builtins.fromTOML` and directory listings, implementing Cargo's documented target auto-discovery: `src/main.rs`, `src/bin/*.rs` and `src/bin/*/main.rs`, `examples`, `tests`, `benches`, the `auto*` switches, explicit target tables merged with discovered ones, custom `path =`, and `test`/`bench` flags.

`required-features` is ignored during prediction, because deciding it would need feature resolution. The prediction is a superset of what Cargo builds, computed separately for build and test plans. Instantiation fills each predicted root with:

- the real root, when the plan contains it;
- for a product the plan lacks, a stub derivation that fails with the reason ("`admin-cli` was not built by Cargo in variant `release`: required features `[cli]` not enabled");
- for a test run the plan lacks, a stub that succeeds and logs that the test was skipped, as `cargo test` does.

A root in the plan that was not predicted is an error listing both sets, because it means the discovery implementation has a bug. Each predicted root also carries its platform: `host` for a target Cargo builds for the build machine (a proc macro's unit tests), else `target`. A test run's `system` and runner depend on it, so dynamic-derivation mode needs it at evaluation time. A root the plan builds for the other platform is an error too. A single "all roots" output was rejected because building any one product would then build every product.

The prediction covers every member, whether a plan selects it or not; an unselected member's roots are stubs. Cargo's `-p` also accepts a path package that is not a member, such as a path dependency outside the workspace. Such a package's roots are predicted for a plan only when its selection names the package, from the package's own manifest and the manifest of its workspace root, if it has one.

The escape hatch is the workspace's `roots` option. [`roots.build`](../../reference/options/workspaces.md#workspacesnamerootsbuild), `roots.test` and `roots.bench` list the roots of each plan kind by name, as the error prints them. A list replaces the prediction for that plan kind, for every target and variant, in both delivery modes. Each entry takes the platform predicted for that root, or `target` when the root is not predicted, unless it sets `platform`. A listed root that the plan lacks becomes a stub, as a predicted one does. [`roots.doctests`](../../reference/options/workspaces.md#workspacesnamerootsdoctests) lists the packages whose doctests the test plans expect ([The root shape](#the-root-shape)).
