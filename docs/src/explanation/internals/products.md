# Products, stages and tests

A product is a package's linked output passed through named stages, each its own derivation, ending in an installed layout. Checks hang off stages, and test binaries become test runs. This page covers stage ordering, checks, stage helpers, debug outputs, and how tests and doctests run.

Every product starts at a fixed stage named `linked` and passes through an ordered set of named stages. Each stage is one content-addressed derivation. Checks hang off stages without joining the chain.

## The `linked` stage

`linked` is a small derivation that symlinks the root unit's output. In IFD mode it depends on the root unit like any derivation. In dynamic-derivation mode it depends on the root derivation of `lib/dynamic.nix`, which depends on `builtins.outputOf <outer drv>."<root>.drv" "out"` (the wrapper), so Nix resolves both at build time; the path goes through three symlinks (root, wrapper's `root`, unit output), which is harmless. Either way, later stages get an ordinary derivation to depend on.

## Stage ordering

```nix
stages.<name> = {
  after = "linked";   # or another stage; default: the previous stage in the preset's chain
  before = null;
  run = { input, product, target, pkgs }: <derivation>;   # input = previous stage's output
};
```

- The effective stage set is the preset's defaults merged with the target's and the package's stage modules. `lib.mkForce null` removes a stage.
- Order comes from `lib.toposort` over the `after` and `before` constraints. A cycle, or a reference to a missing stage, fails evaluation and lists every stage with its constraints.
- The last stage in the order is the product. The `install` stage normalizes the layout (`bin/`, `lib/`). Every stage runs before it unless it is ordered after it: by `after = "install"`, or by being after a stage that is (counting only stages that name `install` would make a stage after a post-install stage also run before `install`, a cycle). Stages before `install` see the flat link output, which the helpers expect; stages after it see the installed layout. `install = null` removes it. It looks each top-level file up in the product's `rootFiles` first: `mkProducts` maps each root's file name in `linked` (a bin's `<target><executableSuffix>`, a library's prefix, crate name and suffix for its kind) to the root's kind at evaluation time, from the roots' `breakbulkRoot.kind` and `.target`, which dynamic-derivation mode's predicted roots carry too. A bin goes to `bin/`, a staticlib to `lib/`, a cdylib or dylib to the traits' `sharedLibraryDir`. `mkLinked` fails when two roots produce one file name, so the map is unambiguous; it also uplifts a staticlib's file to Cargo's name, without the `-C extra-filename` hash. Files not in the map (renamed or added by a stage, import libraries, debug side files) go by the traits' suffixes (`executableSuffix`, `sharedLibrarySuffix`, `staticLibrarySuffix`, `debugArtifacts`), so a MinGW staticlib or import library (`.a`) and an Apple `.dylib` land in `lib/`; a suffix that executables and shared libraries share (`.wasm`) decides nothing. Directories are copied unchanged on every target, so `bindgen`, which writes its output to `pkg/`, owns that directory.

  Files that build scripts placed next to the binaries (Cargo's `target/<profile>`, a run's `targetDirs`; #23) are not in a product by default. The `buildScriptFiles` stage helper copies them in before `install`, and the default `buildScriptFiles` check fails when there are such files and the product holds none of that name, printing the stage with its position in that product's order, or how to remove the check.

  The files considered are those of the target-platform runs the product's roots depend on (`buildScriptRuns` of each root in `units.json`, from the plan's dependency graph), not every run of the plan as in Cargo's shared `target/<profile>`: a product is not asked for a library only another member's dependency places.

  In dynamic-derivation mode each product root's `breakbulk-root.json` lists those runs' `flags` (`buildScriptFlags`), read at build time; they are built before the root anyway. The check is on every product in both modes and passes when nothing was placed.

  The default `buildScriptPaths` check reads the same runs. A run whose script declared `rerun-if-changed` paths that were not in its view lists them in its `flags` (`missing-paths.json`: each path as printed, resolved, and the hint the run's warning gives), and the check fails naming all of them, minus those its `allow` matches by package name and path glob. A check rather than a failing run: the product and everything above the run still build, and one failure lists every such path below the product. It is `on = "linked"`, so it does not wait for the stages. Runs for the build machine (those of build dependencies and proc macros) and runs only test units depend on are not below any product's roots in this sense; for them the run's warning in its build log is all there is.

  The same runs are what a stage can read about the build scripts below its product ([Build-script runs](../../reference/stage-functions.md#build-script-runs)). Every run's `flags` has a `metadata.json` naming its package, version and `links`, its metadata and its `OUT_DIR`, which also makes `flags` reference the run's `out`, so a stage that depends on `flags` can read the `OUT_DIR`. The lookups (`buildScriptLookups`, used by `buildScriptPath`) are shell functions that read these files when the stage builds, not at evaluation: in dynamic-derivation mode the runs are known only then, and both modes share one implementation and one set of failure messages. A package is found by name, and a `links` value by name and key, as a dependent's build script sees `DEP_<LINKS>_<KEY>`; Cargo allows one package per `links` name in a graph, while two versions of one package can both have runs below a product, so a package lookup without a version fails naming them.
- Every stage and check derivation runs through a guard: its builder is wrapped so that, when its input holds the no-binaries marker (`breakbulk-no-binaries`, written by a dynamic-mode `linked` stage whose roots Cargo all skipped), it copies the marker to each of its outputs and succeeds without running the real builder. The wrap goes through `overrideAttrs` when the derivation has it (`mkDerivation`, `runCommand`); a stage or check written as a bare `derivation` call is rebuilt from its `drvAttrs` with the guard as builder and its own builder and arguments passed through, and is guarded the same way. Content addressing ([`ca`](../../reference/options/repository.md#ca)) reaches such a derivation the same way.

## Checks

```nix
checks.<name> = { on = "linked"; run = { input, product, pkgs }: <derivation>; };
```

Each check becomes `repo.checks."<ws>/<triple>/<pkg>/<name>"` (another variant's: `<ws>/<triple>/variant-<v>/<pkg>/<name>`). Every product gets `noSourceReferences` by default, which fails if the main output's runtime closure contains a source-view or crate-source store path, or one of the Rust toolchain's (rustc, its sysroot, cargo, a rust-overlay toolchain's components such as rust-src): a std panic location that names rust-src, or an embedded tool path, would make the toolchain a runtime dependency.

The `debug` output is exempt. A source named only by files matching the product's `sourcesAllowedIn` globs is allowed: `mkProducts` lists each staticlib root's archive there, under rustc's name (`lib<crate>-*.a`) and the uplifted one, because the final link consumes the archive's debug information. The helper's `sourcesAllowedIn` option replaces the list. One toolchain reference is allowed: a toolchain path holding a shared library the checked output itself loads, read from its files (ELF `NEEDED`, PE imports) and looked up in that path's `lib`, `bin` and `lib/rustlib/<target>/{lib,bin}`.

So a binary linked with `-C prefer-dynamic` may reference the sysroot its `libstd-*.so` comes from (nixpkgs' `rustc.unwrapped`); rustc's own component, cargo and rust-src hold no such library and are never allowed. A rust-overlay toolchain's joined sysroot carries its rustc and cargo components in its closure, so a `prefer-dynamic` binary that names it still fails. `noSourceReferences { toolchain = [ ]; }` checks sources only.

Debuginfo side files: when a root unit has a `debug` output (always in dynamic-derivation mode, where unit outputs are not known at evaluation), the `linked` stage has a second output, `debug`, with the root units' `.pdb`, `.dwp` and `.dwo` files under the names Cargo uplifts them to (a bin's `.dwp` as `<bin>.dwp`; `.pdb` and `.dwo` under rustc's names, which the binaries record), and the `.dwo` files of the libraries below each root (each product root in `units.json` lists those units as `debugUnits`; in dynamic-derivation mode the root's wrapper links all of them into its `debug` directory). A unit below counts only when it writes the target traits' per-object side files (`CompileUnit::writes_per_object_debug_files`: `.dwo` with `split-debuginfo = "unpacked"`), not whenever it has a `debug` output: a library that is also a cdylib links its own shared library and has the `.dwp` (`packed`) or `.pdb` (msvc) of that link there, which the product does not ship, and whose contents for the binary the binary's own link already holds (`products-cdylib-debug-packed`, `products-cdylib-debug-unpacked`). On msvc, rustc supports only `packed` (rustc_target `spec/base/msvc.rs`, `supported_split_debuginfo`) and the traits declare no per-object artifact, so no unit below a root counts.

Stages see it as `product.linkedDebug`. `splitDebug` copies the files into its `debug` output.

A binary's skeleton units name their `.dwo` files by rustc's absolute build path (`/build/out/…`), which gdb opens only as given, so `splitDebug` packs the `.dwo` files each binary names into `<binary>.dwp` with `llvm-dwp` (binutils' `dwp` cannot read DWARF 5 units; as rustc's own `.dwp` with `packed`, gdb finds it next to the separate debug file) and drops the loose `.dwo` files; without an earlier stage that splits debug information, `install` writes them to its own `debug` output in the install layout (`$debug/bin/app.pdb` for `$out/bin/app.exe`).

`products.<pkg>.debug` is the `debug` output of the last stage that has one, so a stage after `install` without one (a wrapper, a signer) keeps `splitDebug`'s or `install`'s. A stage that moves binaries must give the moved PDBs its own `debug` output, since Windows debuggers find a PDB next to its `.exe`. On msvc the PDB references the sources and the rlibs it was linked from; the main output references neither.

The debug outputs are tested with debuggers, not only for presence (`products-source-paths`, `products-source-paths-dwp`, `products-source-paths-dwo`, `products-source-paths-dwo5`, `msvc-x86_64-pdb`): with only `$debug/lib/debug` as gdb's `debug-file-directory`, gdb stops in a dependency crate, prints a backtrace into the binary's crate with file and line, and reads the source from the source view the debug output references, also with `split-debuginfo = "packed"` and `"unpacked"` (the latter with DWARF 4 and 5; where gdb must show the dependency's arguments, which only the DWARF objects hold, and does not without the `.dwp`); on msvc, `llvm-symbolizer` resolves the address of `main` (from the PDB's public symbols) in the `.exe` with the debug output's PDB next to it to the function and `src/main.rs:<line>` in the source view.

## Stage helpers

The helpers are in `lib/stage-helpers/default.nix`. Each is made with `mkHelper` from a name, a description, a kind (`stage` or `check`) and option declarations (`mkOption`). The result is an attribute set with a `__functor`, so it is a function that also carries its declaration. Called with options, it checks them with `lib.evalModules` (under the helper's name, so an error names `<helper>.<option>`) and returns the helper with those options set; called with the stage arguments (recognised by `input`), it builds the stage. [Stage helpers](../../reference/stage-helpers.md) is generated from the declarations (`docs/stage-helpers.nix`; `nix run .#update-docs-options`, checked by `docs-options-fresh`); [Stage and check functions](../../reference/stage-functions.md) lists what a stage gets.

| --- | --- |
| [`splitDebug`](../../reference/stage-helpers.md#splitdebug) | Reads the GNU build ID, writes `$debug/lib/debug/.build-id/<xx>/<rest>.debug` with `objcopy --only-keep-debug`, then strips debug info and adds a debuglink. A packed `<bin>.dwp` (`split-debuginfo = "packed"`) moves next to that file, where gdb looks for it (`<debug file's directory>/<binary name>.dwp`; gdb 17.2 `gdb/dwarf2/read.c`, `open_and_init_dwp_file`), with a symlink at its install-layout place |
| [`strip`](../../reference/stage-helpers.md#strip) | `strip --strip-debug` (or `--strip-all` when asked) |
| [`patchelfRpath`](../../reference/stage-helpers.md#patchelfrpath) | Adds rpaths for libraries loaded at runtime, after any rpath shrinking |
| [`bindgen`](../../reference/stage-helpers.md#bindgen) | Lockfile-matched `wasm-bindgen` ([where the CLI comes from](../../reference/stage-helpers.md#bindgenwasmbindgen)) |
| [`wasmOpt`](../../reference/stage-helpers.md#wasmopt) | `wasm-opt` on a core module |

| [`deterministicZip`](../../reference/stage-helpers.md#deterministiczip) | Sorted entries, fixed timestamps, no extra attributes |

| [`buildScriptPaths`](../../reference/stage-helpers.md#buildscriptpaths) | A check, on every product: fails when a build script below it declared a `rerun-if-changed` path missing from its view, naming each path and the option to add it to |
| [`noSourceReferences`](../../reference/stage-helpers.md#nosourcereferences) | A check, on every product: no source or toolchain path in the main output's closure (above) |

## Tests

- **Test binaries** are roots with `test = true` in the test plan. `tests.<pkg>.<name>` is the binary installed as `bin/<target><exe suffix>`, the suffix from the target's traits (`.exe` on Windows, `.wasm` for wasm, none on Linux), as Cargo names it; `benches.<pkg>.<name>` likewise. Test binaries are never stripped.
- **`CARGO_BIN_EXE_<name>`** is compile-time env recorded by the planner. Cargo points it at the bin's uplifted copy, `<profile dir>/<name><exe suffix>`, and the planner rewrites that path to the file in the output of the same plan's compile unit of that bin: in a test plan the plain bin `cargo test` builds for the integration tests, which is not a root and has no `linked` stage. The test's compile unit therefore depends on that bin unit. A bin unit stores its file under Cargo's uplifted name (`<name>` and the traits' `executableSuffix`), not rustc's `<crate name>-<hash>`, so `argv[0]` and `std::env::current_exe()` give the name they give under Cargo. Examples are stored the same way; test and bench executables keep rustc's hashed names, as under Cargo.
- **`CARGO_TARGET_TMPDIR`** is also compile-time env, but must be writable when the test runs. It is rewritten to the fixed path `/tmp/breakbulk-target-tmp`, and the test-run derivation creates that path before running (see spikes). In the sandbox `/tmp` is private to the build; unsandboxed builds share it (#21).
- **Test runs** are one derivation per test binary. A small CA derivation copies the test binary, and the test run consumes that copy, so a byte-identical binary does not re-run.

  With `test.stripForRun` the copy is stripped of debug info and of its GNU build ID (`objcopy --strip-debug --remove-section=.note.gnu.build-id`; the linker computes the ID over the whole file), because the debug info of the workspace libraries it links names their source views; files that are not ELF are copied as they are. Without `ca` the stripped copy is input-addressed.

  With [`test.runFiles`](../../reference/options/packages.md#packagesnametestrunfiles) the working directory and the runtime `CARGO_MANIFEST_DIR` (and `CARGO_MANIFEST_PATH`, which then may not exist) are the package directory of the narrowed view; a test reading another file fails. Test apps keep the package's whole view and the unstripped binary.

  With `ca`, the paths a run's spec names that change with unrelated edits are replaced by small CA copies: the dynamic-library path's entries (their files only) and the package's build-script `rustc-env` values. An edit to a package with a build script below the test then does not re-run it when its binary is byte-identical.

  In dynamic-derivation mode a test run does not read the root's wrapper. The wrapper's closure holds the package's whole source view (its `breakbulk-root.json` names it) and the unit's debuginfo. Instead, one small derivation per run copies what the run needs out of it: the spec, narrowed to the `"run"` view ([source views](sources.md#source-views)) and without nextest's metadata for a libtest run, and, when the run takes no copy of the binary, a link to it. So a run's input closure is the same as in IFD mode, with `ca` and without. With `ca` this derivation is content-addressed and does what IFD mode does above, at build time: it holds the `rustc-env` values in place of the build scripts' `flags`, and, in a second output, the dynamic-library copies (one name for every run, so runs with the same copies share them).

  The run uses the `runner` of the test's platform, with the package source view as the working directory (as Cargo does), a fresh, empty `HOME` at `$TMPDIR/home` (set first, so `[env]` and `test.env` can replace it; test apps keep the user's), plus Cargo's runtime env (`CARGO_MANIFEST_DIR`, `CARGO_PKG_*`), the package's [`test.env`](../../reference/options/packages.md#packagesnametestenv), and [`test.path`](../../reference/options/packages.md#packagesnametestpath) on `PATH`.

  Its `system` is the target's [`testSystem`](../../reference/options/targets.md#targetsnametestsystem) when set.

  Cargo picks the runner and the libraries by the test unit's compile kind (`target_runner(unit.kind)`, `Compilation::fill_env`). A proc macro's unit tests are a host unit: Cargo builds them for the build machine (`CompileKind::for_target`), so in a cross plan they run there, with the host's runner (the native target's `runner`, normally none, as Cargo looks the runner up under the host triple), the host's dynamic-library variable and the host's sysroot library directory, not under the target's runner or on `testSystem`. Each root records its platform (`breakbulkRoot.platform`, `host` or `target`). Dynamic-derivation mode must know it at evaluation time, to choose the run's `system`, so it takes the prediction: a proc macro (`proc-macro = true` or a `proc-macro` crate type) is the host's. Instantiation fails when the plan builds a root for another platform than predicted. Test apps choose the same way. `testPlatforms` in `lib/test-runs.nix` holds the choice for both modes.

  Its dynamic-library path holds the search paths that pass the dynamic-library rule (see [Directive parsing](../../reference/unit-builder.md#directive-parsing)) of the runs of the test's platform that its binary depends on, the bins it names in `CARGO_BIN_EXE_<name>` included. Then comes the sysroot's library directory for the platform's triple, from a small derivation holding only that directory's shared libraries (so a test run does not depend on the whole toolchain). Cargo instead puts every run of the build on the path, because its runs share one `target/<profile>` and it keeps one set for the whole build (`Compilation::native_dirs`). The test's own runs are enough: Cargo links a unit against the search paths of the build scripts in its closure only (`add_native_deps`, over `build_scripts.to_link`), so a library the test was linked against is found again through them. So a failing build script blocks only the tests that depend on it, and an edit re-runs only the tests below it. A test that loads, by name, a library that a build script outside its closure placed (an unrelated crate's) passes under `cargo test` and fails here: make that crate a dev-dependency, or, for a library from nixpkgs, put it in the package's `test.env` or inputs.

  The variable that holds it is the test process's platform's, not always the build machine's: the runner's when it declares one (wine reads `WINEPATH`, `;`-separated, and finds no DLL on the Unix `PATH` or `LD_LIBRARY_PATH`; checked with wine 11.0), else the target's traits (`dylibPathVar`: `LD_LIBRARY_PATH` on Linux, `PATH` on Windows run natively), and none for wasm.

  Cargo on a Linux host sets `LD_LIBRARY_PATH` for a Windows runner too, so a Windows test that loads a DLL its build script built fails under `cargo test` with wine and passes in breakbulk (`windows-dll-*` in `tests/presets/extra-targets.nix`).

  The variable of recorded processes (compiles and build-script runs, which always run on the build machine) is the build machine's, one constant (`breakbulk_unit::splice::DYLIB_PATH_VAR`, re-exported by breakbulk-format as `HOST_DYLIB_PATH_VAR`). It succeeds on exit 0. The output goes to the build log and to `$log` in `$TMPDIR`, never to `$out` (an empty directory), so that a passing run is reproducible under `nix build --rebuild`. After a passing run, a subshell runs the snippets of `postRunSnippets` (`lib/test-runs.nix`) in order: the coverage profiles' move into `$out/profraw` (renamed by content: `LLVM_PROFILE_FILE`'s `%p` is a process ID), the package's `test.postRun`, the binary's, and `keepLog`'s copy. Dynamic-derivation mode's runs use the same snippets.
- **Skipped tests:** a predicted test the plan lacks gets a test-run stub that succeeds and logs the reason.
- **Test arguments:** [`test.args`](../../reference/options/packages.md#packagesnametestargs) and `test.binaries.<binary>.args` are passed to the binary; [`includeIgnored`](../../reference/options/packages.md#packagesnametestincludeignored) adds `--include-ignored`. They are part of the test-run derivation, so changing them re-runs only the affected runs. `enable = false` leaves a binary's run out of `repo.checks`. `test.binaries.<binary>.env` adds to `test.env` for that binary's run. Last, every test run sets `RUST_TEST_THREADS=$NIX_BUILD_CORES` if nothing before set it (`[env]`, `test.env`, the binary's `env`). nextest does not read that variable, so a nextest run also passes a tool config file (`--tool-config-file`) whose default profile sets `test-threads` to `$NIX_BUILD_CORES`. nextest ranks a tool config file below the project's configuration and below `NEXTEST_TEST_THREADS`, so both still win ([threads](../products.md#tests)).
- **Test apps:** each test binary also gets a runnable app with the test run's working directory, environment and runner, run on the user's machine. It is the escape hatch for tests that need network, and the way to rerun one binary under a debugger or with a filter. Network access inside `nix flake check` (through a fixed-output test run) is a possible later addition; impure derivations are not used.
- **nextest.** Test binaries run directly (libtest) by default. With `test.runner = "nextest"`, each test run synthesizes the `binaries-metadata` file that nextest's reuse-build mode reads, so per-test retries, timeouts, test groups and default filters from the nextest config apply; each binary is still its own test run. The cargo metadata it synthesizes with it lists every path package of the test plan with its Cargo targets and the dependencies between them (the plan's `pathPackages`), so filters with `binary()`, `binary_id()`, `deps()` and `rdeps()` match as under Cargo. The standard library's packages under `-Zbuild-std` are not listed, as `cargo metadata` does not list them. The cost: adding or renaming a target anywhere in the workspace re-runs every nextest run. The setting is per package ([`packages.<name>.test.runner`](../../reference/options/packages.md#packagesnametestrunner), `.nextest.{profile,configFile,package}`), with a workspace-wide default in [`workspaces.<ws>.memberDefaults`](../../reference/options/workspaces.md#workspacesnamememberdefaults) that a package's own non-null setting overrides.
- **Doctests:** one derivation per library crate, from the test plan's traced `rustdoc --test` command. Inputs are the crate's `rlib`, its dependencies with test-plan features, and the source view. Cargo gives `rustdoc --test` an `-L` for every run in the invocation, sorted by value. The derivation keeps only the runs of its platform in its own closure, by the same rule as test runs: it depends on their `flags` outputs and rebuilds the sorted list from them at build time. Its dynamic-library path, which Cargo fills with every host run's in-`out` search paths, keeps the host runs in its closure (those of the proc macros rustdoc loads). It gets no `-l`. It runs under the runner of its platform, as Cargo picks the runner by compile kind: a library's doctest runs under the target's runner; a proc macro's doctest is a host unit (no `--target`), so it runs on the build machine with no runner. As a test run, it gets a fresh, empty `HOME` at `$TMPDIR/home` (`breakbulk-unit` puts it in layer 1, so `test.env` can replace it); its output goes to the build log and `$TMPDIR`, and `$out` is empty. The package's `postRun` snippets and `keepLog`'s copy become one script (`BREAKBULK_TEST_POST_RUN`, with stdenv's basic tools on `PATH`), which `breakbulk-unit doctest` runs after passing doctests. It appears in `repo.checks`. There is no cutoff, because compiling and running happen in one rustdoc process. If the toolchain cannot run doctests for a cross target, the derivation is a stub that logs why.
- **Benches:** `cargo test --no-run` builds no benches, so the test plan has none. Bench binaries come only from the bench variant (`cargo bench --no-run`, bench profile), exposed for running outside Nix. With [`benchSmoke`](../../reference/options/workspaces.md#workspacesnamebenchsmoke), each bench binary also runs once with `--test` as a check. Timed runs never happen inside Nix.

## Documentation

Each variant on each target has a doc plan, traced from `cargo doc` (with `--no-deps` under [`docs.noDeps`](../../reference/options/workspaces.md#workspacesnamedocsnodeps), the default), and one docs derivation, `target.<triple>.docs`. The plan is traced only when the docs are used.

- **Units.** rustdoc reads its dependencies' metadata, so Cargo checks them (`compute_deps_doc` in cargo's `unit_dependencies.rs`: check mode for libraries, a real build for proc macros) and runs their build scripts. These units are the plan's units, and they are the same derivations as a check variant's of the same profile and features: Cargo hashes no "doc" into their `-C metadata`. A clippy variant's doc plan is traced without clippy-driver, so its members' units are the check variant's too.
- **One derivation.** rustdoc writes each crate into one folder and merges the cross-crate files there in place: the search index, `crates.js`, `src-files.js` and the implementor lists under `trait.impl/` and `type.impl/` (`write_shared` in rustdoc's `html/render/write_shared.rs`, with the default `--merge=shared`). The options that write each crate's part apart and merge them in a final step (`--write-doc-meta-dir`, `--read-doc-meta-dir`, formerly `--parts-out-dir`, `--include-parts-dir` and `--merge`) are unstable in rustdoc 1.99, and Cargo uses them only with `-Zrustdoc-mergeable-info`. So the docs derivation, `breakbulk-unit docs`, runs every traced rustdoc command in turn with `-o $out`. As Cargo does, it removes the crate's own directory first; it removes rustdoc's `.lock` at the end.
- **Order.** rustdoc links to another crate's items only when that crate's directory is already in the output folder when it starts (`ExternalCrate::location` in rustdoc's `clean/types.rs`); otherwise a crate without `html_root_url` gets no link. Cargo documents a dependency before its dependents when it documents both, but under `--no-deps` it does not order the members' rustdocs, so whether `util`'s docs link to `base`'s depends on which ran first. The plan runs each command after the documented crates it reads (its `--extern`s), and otherwise by crate name: every link that can resolve does, and the result does not change from one plan to the next. Cargo passes `--extern-html-root-url` only with `-Zrustdoc-map`.
- **One folder.** With `--target`, Cargo documents a proc macro into its host directory, `target/doc`, and every other crate into `target/<triple>/doc`, so the target's pages do not link to the proc macro's. breakbulk always passes `--target`, so that rustflags stay off host units; the docs derivation writes every crate into its one output, as Cargo does without `--target`.
- **Inputs.** Each command's dependency directory holds the `rmeta` of every crate below it, and a proc macro's library; its build scripts' `flags` give its `--cfg`, `--check-cfg` and env, as for a compile. The derivation names all of them as inputs: it reads no manifests.

A crate outside the workspace (a registry or git crate, documented with `docs.noDeps = false`) has its source pages describe its source by its absolute path, as under Cargo; here that is the crate's store path, so the docs reference those sources.
