# Products, stages and tests

A product is a package's linked output passed through named stages, each its own derivation, ending in an installed layout. Checks hang off stages, and test binaries become test runs. This page covers stage ordering, checks, stage helpers, debug outputs, and how tests and doctests run.

Every product starts at a fixed stage named `linked` and passes through an ordered set of named stages. Each stage is one content-addressed derivation. Checks hang off stages without joining the chain.

## The `linked` stage

`linked` is a small derivation that symlinks the files of each root's wrapper `root` ([The root shape](instantiation.md#the-root-shape)), leaving out a root whose wrapper says Cargo did not build it (`not-built`). In dynamic-derivation mode the wrapper is `builtins.outputOf <outer drv>."<root>.drv" "out"`, so Nix resolves it at build time. Either way, later stages get an ordinary derivation to depend on.

## Stage ordering

```nix
stages.<name> = {
  after = "linked";   # or another stage; default: the previous stage in the preset's chain
  before = null;
  run = { input, product, target, pkgs }: <derivation>;   # input = previous stage's output
};
```

- The effective stage set is one option's value, merged by the module system (`mergeSets` in `lib/products.nix`) from three layers, lowest first: the stages `debugInfo` inserts, `targets.<t>.stages` (where a preset's chain is defined, `mkDefault` per field), and the package's `stages`. Each stage is a submodule (`bt.stage`, lib/modules/types.nix), so its fields merge across layers; a layer is ranked (`bt.layer`) so that a higher layer's single values win at equal priority, and a priority around a whole set (`stages = lib.mkForce { … }`) still drops the lower layers' definitions. `null` removes a stage: it stands for `{ enable = false; }`.
- Order comes from `lib.toposort` over the `after` and `before` constraints. A cycle, or a reference to a missing stage, fails evaluation and lists every stage with its constraints.
- A stage with no `after` runs after the stages the target's `debugInfo` inserts (`leading` in `explainOrder`), unless it is ordered before one of them. Those stages differ by target (`packDwo` only on ELF), so without this a stage set that orders on one target would be ambiguous on another.
- The last stage in the order is the product. `mkProduct` renames its derivation to the product's `drvName` (`<pkg>-<version>` in `mkProducts`) rather than each helper naming itself so, since a stage after `install` (`adhocSign`, `zip`) cannot know it is the last. It adds `meta` with `extendDerivation`, which changes no derivation: `mainProgram` is the package's one bin, or Cargo's `default-run`, when `install` is a stage, under the name `install` gives it in `bin/`, and `packages.<pkg>.meta` goes over it. The `install` stage normalizes the layout (`bin/`, `lib/`). Every stage runs before it unless it is ordered after it: by `after = "install"`, or by being after a stage that is (counting only stages that name `install` would make a stage after a post-install stage also run before `install`, a cycle). Stages before `install` see the flat link output, which the helpers expect; stages after it see the installed layout. `install = null` removes it. It looks each top-level file up in the product's `rootFiles` first: `mkProducts` maps each root's file name in `linked` (a bin's `<target><executableSuffix>`, a library's prefix, crate name and suffix for its kind) to the root's kind at evaluation time, from the predicted roots' `breakbulkRoot.kind` and `.target`. A bin goes to `bin/`, a staticlib to `lib/`, a cdylib or dylib to the traits' `sharedLibraryDir`. `mkLinked` fails when two roots produce one file name, so the map is unambiguous; it also uplifts a staticlib's file to Cargo's name, without the `-C extra-filename` hash. Files not in the map (renamed or added by a stage, import libraries, debug side files) go by the traits' suffixes (`executableSuffix`, `sharedLibrarySuffix`, `staticLibrarySuffix`, `debugArtifacts`), so a MinGW staticlib or import library (`.a`) and an Apple `.dylib` land in `lib/`; a suffix that executables and shared libraries share (`.wasm`) decides nothing. Directories are copied unchanged on every target, so `wasmBindgen`, which writes its output to `pkg/`, owns that directory.

  Files that build scripts placed next to the binaries (Cargo's `target/<profile>`, a run's `targetDirs`; #23) are not in a product by default. The `buildScriptFiles` stage helper copies them in before `install`, and the default `buildScriptFiles` check fails when there are such files and the product holds none of that name, printing the stage with its position in that product's order, or how to remove the check.

  The files considered are those of the target-platform runs the product's roots depend on (from the plan's dependency graph), not every run of the plan as in Cargo's shared `target/<profile>`: a product is not asked for a library only another member's dependency places.

  Each product root's `breakbulk-root.json` lists those runs' `flags` (`buildScriptFlags`), read at build time; they are built before the root anyway. The check is on every product and passes when nothing was placed.

  Missing `rerun-if-changed` paths are checked per plan, not per product ([Missing build-script paths](#missing-build-script-paths)).

  The same runs are what a stage can read about the build scripts below its product ([Build-script runs](../../reference/stage-functions.md#build-script-runs)). Every run's `flags` has a `metadata.json` naming its package, version and `links`, its metadata and its `OUT_DIR`, which also makes `flags` reference the run's `out`, so a stage that depends on `flags` can read the `OUT_DIR`. The lookups (`buildScriptLookups`, used by `buildScriptPath`) are shell functions that read these files when the stage builds, not at evaluation: in dynamic-derivation mode the runs are known only then, and both modes share one implementation and one set of failure messages. A package is found by name, and a `links` value by name and key, as a dependent's build script sees `DEP_<LINKS>_<KEY>`; Cargo allows one package per `links` name in a graph, while two versions of one package can both have runs below a product, so a package lookup without a version fails naming them.
- Every stage and check derivation runs through a guard: its builder is wrapped so that, when its input holds the no-binaries marker (`breakbulk-no-binaries`, written by a dynamic-mode `linked` stage whose roots Cargo all skipped), it copies the marker to each of its outputs and succeeds without running the real builder. The wrap goes through `overrideAttrs` when the derivation has it (`mkDerivation`, `runCommand`); a stage or check written as a bare `derivation` call is rebuilt from its `drvAttrs` with the guard as builder and its own builder and arguments passed through, and is guarded the same way. Content addressing ([`ca`](../../reference/options/repository.md#ca)) reaches such a derivation the same way.

## Missing build-script paths

A run whose script declared `rerun-if-changed` paths that were not in its view lists them in its `flags` output (`missing-paths.json`: each path as printed, resolved, and the hint the run's warning gives); its `metadata.json` names the package, its version and the platform the run was for. Each build and test plan of a variant has one `buildScriptPaths` check (lib/build-script-paths.nix) over every build-script run of the plan, on both platforms: the runs below the products, the runs for the build machine (build dependencies, proc macros and their dependencies), and the runs only test units depend on. It fails naming every missing path with its package, version and the run's platform, minus those the package's `buildScriptPaths.allow` matches. The table of allowed paths is built at evaluation time from each lockfile entry's merged package settings for the plan's target and variant, keyed by name and version, and the check matches each run against it when it builds.

A check rather than a failing run: everything above the run still builds, and one failure lists every such path of the plan. Per plan rather than per product: the runs for the build machine and those only tests depend on are below no product's roots, and a path is named once, not by every product above it.

The check reads the runs without building the rest of the plan, through the plan's `runs.drv` wrapper ([The root shape](instantiation.md#the-root-shape)), a derivation that depends on the `flags` output of every run of the plan and lists them in `$out/runs`. `units.drv`, which check variants build, would build every compile of the plan too.

## Checks

```nix
checks.<name> = { on = "linked"; run = { input, product, target, pkgs }: <derivation>; };
```

Each check becomes `repo.checks."<ws>/<triple>/<pkg>/<name>"` (another variant's: `<ws>/<triple>/variant-<v>/<pkg>/<name>`). The check set merges as the stage set does, over `defaultChecks` (`lib/products.nix`), the lowest layer: `noSourceReferences` (`null` there when the variant's `sourcePaths` is `"keep"`) and `buildScriptFiles`. `noSourceReferences` fails if the main output's runtime closure contains a source-view or crate-source store path, the workspace's vendor directory (which a nested Cargo in a build script compiles from), or one of the Rust toolchain's (rustc, its sysroot, cargo, a rust-overlay toolchain's components such as rust-src): a std panic location that names rust-src, or an embedded tool path, would make the toolchain a runtime dependency.

The `debug` output is exempt. A source named only by files matching the product's `sourcesAllowedIn` globs is allowed: `mkProducts` lists each staticlib root's archive there, under rustc's name (`lib<crate>-*.a`) and the uplifted one, because the final link consumes the archive's debug information. The helper's `sourcesAllowedIn` option replaces the list. One toolchain reference is allowed: a toolchain path holding a shared library the checked output itself loads, read from its files (ELF `NEEDED`, PE imports) and looked up in that path's `lib`, `bin` and `lib/rustlib/<target>/{lib,bin}`.

So a binary linked with `-C prefer-dynamic` may reference the sysroot its `libstd-*.so` comes from (nixpkgs' `rustc.unwrapped`); rustc's own component, cargo and rust-src hold no such library and are never allowed. A rust-overlay toolchain's joined sysroot carries its rustc and cargo components in its closure, so a `prefer-dynamic` binary that names it still fails. `noSourceReferences { toolchain = [ ]; }` checks sources only.

Debuginfo side files: the `linked` stage has a second output, `debug` (whether a root unit has one is known at build time only), with the root units' `.pdb`, `.dwp` and `.dwo` files under the names Cargo uplifts them to (a bin's `.dwp` as `<bin>.dwp`; `.pdb` and `.dwo` under rustc's names, which the binaries record), and the `.dwo` files of the libraries below each root (the root's wrapper links all of them into its `debug` directory). A unit below counts only when it writes the target's per-object side files (the plan's `targetDebuginfo`) (`CompileUnit::writes_per_object_debug_files`: `.dwo` with `split-debuginfo = "unpacked"`), not whenever it has a `debug` output: a library that is also a cdylib links its own shared library and has the `.dwp` (`packed`) or `.pdb` (msvc) of that link there, which the product does not ship, and whose contents for the binary the binary's own link already holds (`products-cdylib-debug-packed`, `products-cdylib-debug-unpacked`). On msvc, rustc supports only `packed` (rustc_target `spec/base/msvc.rs`, `supported_split_debuginfo`) and its spec declares no per-object artifact, so no unit below a root counts.

Stages see it as `product.linkedDebug`, and the `debug` output of the last earlier stage that has one as `product.earlierDebug`. A stage that writes a `debug` output starts it from `earlierDebug` when there is one, else from the link units' files laid out as `install` lays out their binaries (`$debug/bin/app.pdb` for `$out/bin/app.exe`), so each such stage's `debug` output holds every debug file so far. `packDwo`, `splitDebug` and `strip` do; `install` writes a `debug` output only when no earlier stage has one.

A binary's skeleton units name their `.dwo` files by rustc's absolute build path (`/build/out/…`), which gdb opens only as given, so `packDwo` packs the `.dwo` files each ELF file or `ar` archive names (read from its skeleton units with `readelf`, which walks an archive's members) into `<file>.dwp` with `llvm-dwp` (binutils' `dwp` cannot read DWARF 5 units), under `bin/` or `lib/` as `install` places the file, and drops the loose `.dwo` files. `splitDebug` moves a `<binary>.dwp`, `packDwo`'s or rustc's own with `packed`, next to the separate debug file, where gdb looks for it. `debugInfo` inserts `packDwo` on ELF targets before `splitDebug` (`split`) or alone (`keep`); it is an ordinary stage, so `null` removes it and the loose files ship (`products-pack-dwo-removed`). `strip` drops the `.dwo` files and the `<file>.dwp` of each ELF file it strips, which no skeleton names after it (`products-debug-info-strip`); a `.dwp` that `splitDebug` moved next to a `.debug` file stays, since that file keeps its skeletons. A staticlib's archive keeps its skeleton units for the final link and ships `lib/<archive>.dwp`, which that link's program packs into its own `.dwp` (`products-staticlib-dwp`).

`products.<pkg>.debug` is the `debug` output of the last stage that has one, so a stage after `install` without one (a wrapper, a signer) keeps `splitDebug`'s or `install`'s. A stage that moves binaries must give the moved PDBs its own `debug` output, since Windows debuggers find a PDB next to its `.exe`. On msvc the PDB references the sources and the rlibs it was linked from; the main output references neither.

The debug outputs are tested with debuggers, not only for presence (`products-source-paths`, `products-source-paths-dwp`, `products-source-paths-dwo`, `products-source-paths-dwo5`, `products-debug-info-keep`, `products-staticlib-dwp`, `msvc-x86_64-pdb`): with only `$debug/lib/debug` as gdb's `debug-file-directory`, gdb stops in a dependency crate, prints a backtrace into the binary's crate with file and line, and reads the source from the source view the debug output references, also with `split-debuginfo = "packed"` and `"unpacked"` (the latter with DWARF 4 and 5; where gdb must show the dependency's arguments, which only the DWARF objects hold, and does not without the `.dwp`; with `debugInfo = "keep"`, the same with the `.dwp` next to the binary; for a staticlib, gdb gives a source line of a dependency's function in a C program linked against the archive, with the program's `.dwp` packed from the archive's, and not without it); on msvc, `llvm-symbolizer` resolves the address of `main` (from the PDB's public symbols) in the `.exe` with the debug output's PDB next to it to the function and `src/main.rs:<line>` in the source view.

## Stage helpers

The helpers are in `lib/stage-helpers/default.nix`. Each is made with `mkHelper` from a name, a description, a kind (`stage` or `check`) and option declarations (`mkOption`). The result is an attribute set with a `__functor`, so it is a function that also carries its declaration. Called with options, it checks them with `lib.evalModules` (under the helper's name, so an error names `<helper>.<option>`) and returns the helper with those options set; called with the stage arguments (recognised by `input`), it builds the stage. [Stage helpers](../../reference/stage-helpers.md) is generated from the declarations (`docs/stage-helpers.nix`; `nix run .#update-docs-options`, checked by `docs-options-fresh`); [Stage and check functions](../../reference/stage-functions.md) lists what a stage gets.

A packed `<bin>.dwp` (`split-debuginfo = "packed"`) moves next to that file, where gdb looks for it (`<debug file's directory>/<binary name>.dwp`; gdb 17.2 `gdb/dwarf2/read.c`, `open_and_init_dwp_file`), with a symlink at its install-layout place |
| [`strip`](../../reference/stage-helpers.md#strip) | `strip --strip-debug` (or `--strip-all` when asked) |
| [`patchelfRpath`](../../reference/stage-helpers.md#patchelfrpath) | Adds rpaths for libraries loaded at runtime, after any rpath shrinking |

## Tests

- **Test binaries** are roots with `test = true` in the test plan. `tests.<pkg>.<name>` is the binary installed as `bin/<target><exe suffix>`, the suffix taken at build time from the binary's own file name (`.exe` on Windows, `.wasm` for wasm, none on Linux), as Cargo names it; `benches.<pkg>.<name>` likewise. Test binaries are never stripped.
- **`CARGO_BIN_EXE_<name>`** is compile-time env recorded by the planner. Cargo points it at the bin's uplifted copy, `<profile dir>/<name><exe suffix>`, and the planner rewrites that path to the file in the output of the same plan's compile unit of that bin: in a test plan the plain bin `cargo test` builds for the integration tests, which is not a root and has no `linked` stage. The test's compile unit therefore depends on that bin unit. A bin unit stores its file under Cargo's uplifted name (`<name>` and the `exe-suffix` of rustc's target spec), not rustc's `<crate name>-<hash>`, so `argv[0]` and `std::env::current_exe()` give the name they give under Cargo. Examples are stored the same way; test and bench executables keep rustc's hashed names, as under Cargo.
- **`CARGO_TARGET_TMPDIR`** is also compile-time env, but must be writable when the test runs. The planner rewrites it to the relative path `target/tmp`, which resolves against the working directory wherever the binary runs. A test run or test app whose binary contains that string (a byte search) runs in a fresh directory private to the run: a symbolic link per entry of the package directory (its own `target` left out) and a real, empty `target/tmp` (`workdirScript` in `lib/test-runs.nix`). An absolute path cannot be right for runs separated from the build: test apps, unsandboxed builders, copies of the binary run by hand. The binary is not patched, so nothing is re-signed on macOS. Other binaries run in the package directory itself. [Tests](../products.md#tests) lists how this differs from `cargo test`.
- **Run settings.** Each run's settings (`enable`, `args`, `env`, `path`, `preRun`, `postRun`, `wrapper`, `runner`, `stages`) are the package's `test`, refined by `test.doctest` or `bench` and then by `test.binaries.<key>` ([run settings](../configuration.md#run-settings)). Those three are kept as modules, each with the rank of the layer that set it (`bt.subLayers`, as `target` and `variant` are), and `runsOf` in `lib/package-settings.nix` evaluates a run's by extending the package's settings with them under `test`, a kind's at a quarter and a binary's at half of the room between their layer and its `target` layer. A run without its own modules reads the package's evaluation as it is. `lib/test-runs.nix` (`runConfig`) takes each run's settings once per test-runs set, for both delivery modes.
- **Test wrappers** (`wrapper`) start the binary in test runs and test apps: `env … BREAKBULK_NEXT=<target runner script> BREAKBULK_SOURCE_ROOT=<view root> <wrapper> <binary> <args…>` in the working directory above (`launchWords`; a test runner gets the same as one program, its `launcher`). Under `testRunners.nextest` the launcher is the target runner variable (`CARGO_TARGET_<T>_RUNNER`): nextest's own wrapper scripts need the experimental `wrapper-scripts` feature, which only the project's main nextest configuration file can enable.
- **Test runs** are one derivation per test binary. The binary goes through the run's [`stages`](../../reference/options/packages.md#packagesnameteststages) first, as a product's go through its stages (`stages.mkProduct`, without `install` or checks; `runBinary` in `lib/test-runs.nix`), and the run consumes the last stage's output; with `ca` each stage is content-addressed, so a byte-identical result does not re-run. Without a stage, with `ca`, a small CA derivation copies the binary instead.

  With `ca` the default stage is `strip` with `buildId = false`: debug info and the GNU build ID go (`strip --strip-debug --remove-section=.note.gnu.build-id`; the linker computes the ID over the whole file), because the debug info of the workspace libraries it links names their source views. A stage's `target` argument has the platform's `packageSet`, as a product stage's does, and the stages that run binutils on ELF files (`strip`, `splitDebug`, `neededLibraries`) default to that set's C toolchain binutils (for the native target, the stdenv's own, so the stage adds nothing to the closure; for a cross Linux target, the cross binutils its preset links with); for an ELF target without one (bare metal, a custom target), `binutils-unwrapped-all-targets`, which reads any ELF machine. `packDwo` reads the skeleton units' `.dwo` names with `llvm-dwarfdump`, from the LLVM it packs with. A Mach-O file gets `llvm-strip -S`, which removes its debug map. Its UUID (`LC_UUID`) is the build ID's counterpart: lld computes it over the whole file, debug map (object and source paths) included, so it differs whenever the debug map does, and `llvm-strip` keeps it. LLVM's tools cannot remove it, and dyld refuses a dylib without one, and an executable without one once the SDK it records is macOS 26 (dyld's `Policy::enforceHasUUID`), which also rules out linking with `-no_uuid`. So the stage zeroes it, computes a new one (SHA-256 of the file's name and bytes up to the code signature, RFC 9562 version 8 bits), writes it, and runs `llvm-objcopy` on the file, which writes the ad hoc, linker-signed signature again in the form `llvm-strip` left (`identifier` the file's name, 4 KiB page hashes). A universal file keeps its UUIDs: rustc links one architecture per target. Without `ca` there is no default stage: an input-addressed copy saves no run.

  With [`test.runFiles`](../../reference/options/packages.md#packagesnametestrunfiles) the working directory and the runtime `CARGO_MANIFEST_DIR` (and `CARGO_MANIFEST_PATH`, which then may not exist) are the package directory of the narrowed view; a test reading another file fails. Test apps keep the package's whole view and the unstripped binary.

  With `ca`, the paths a run's spec names that change with unrelated edits are replaced by small CA copies: the dynamic-library path's entries (their files only) and the package's build-script `rustc-env` values. An edit to a package with a build script below the test then does not re-run it when its binary is byte-identical.

  A test run does not read the root's wrapper: the wrapper's closure holds the package's whole source view (its `breakbulk-root.json` names it) and the unit's debuginfo. Instead, one small derivation per run (`runInfo` in `lib/test-runs.nix`) copies what the run needs out of it: the spec, narrowed to the `"run"` view ([source views](sources.md#source-views)) and without nextest's metadata for a libtest run, and, when the run takes no copy of the binary, a link to it. With `ca` this derivation is content-addressed and makes the copies above: it holds the `rustc-env` values in place of the build scripts' `flags`, and, in a second output, the dynamic-library copies (one name for every run, so runs with the same copies share them).

  The run uses the target runner of the test's platform, through its test runner, with the package source view as the working directory (as Cargo does), Cargo's runtime env (`CARGO_MANIFEST_DIR`, `CARGO_PKG_*`), the run's [`env`](../../reference/options/packages.md#packagesnametestenv), its [`path`](../../reference/options/packages.md#packagesnametestpath) on `PATH` (packages of the package set of the machine that runs it), and then its [`preRun`](../../reference/options/packages.md#packagesnametestprerun) entries, in the run's shell. The `home` entry gives a fresh, empty `HOME` at `$TMPDIR/home` when the environment left Nix's `/homeless-shelter` (test apps run no entries and keep the user's).

  Its `system` is the target's [`testSystem`](../../reference/options/targets.md#targetsnametestsystem) when set.

  Cargo picks the target runner and the libraries by the test unit's compile kind (`target_runner(unit.kind)`, `Compilation::fill_env`). A proc macro's unit tests are a host unit: Cargo builds them for the build machine (`CompileKind::for_target`), so in a cross plan they run there, with the host's runner ([`workspaces.<ws>.host.runner`](../../reference/options/workspaces.md#workspacesnamehostrunner), normally none, where Cargo looks the target runner up under the host triple; breakbulk keeps host and target settings apart, so the native target's runner does not apply), the host's dynamic-library variable and the host's sysroot library directory, not under the target's runner or on `testSystem`. Each root records its platform (`breakbulkRoot.platform`, `host` or `target`). Dynamic-derivation mode must know it at evaluation time, to choose the run's `system`, so it takes the prediction: a proc macro (`proc-macro = true` or a `proc-macro` crate type) is the host's. Instantiation fails when the plan builds a root for another platform than predicted. Test apps choose the same way. `testPlatforms` in `lib/test-runs.nix` holds the choice for both modes.

  Its dynamic-library path holds the search paths that pass the dynamic-library rule (see [Directive parsing](../../reference/unit-builder.md#directive-parsing)) of the runs of the test's platform that its binary depends on, the bins it names in `CARGO_BIN_EXE_<name>` included. Then comes the sysroot's library directory for the platform's triple, from a small derivation holding only the standard library's shared library from it (`libstd-*`, so a test run does not depend on the whole toolchain). The compiler's libraries in that directory (nixpkgs' rustc has `librustc_driver` and rustc-dev's proc macros there) stay out: a `rustc` that a test starts would load the copied driver and take the copy as its sysroot, and the driver would bring nixpkgs' LLVM into every test run's closure. A `rustc_private` test binary finds the driver through its RUNPATH, which nixpkgs' ld-wrapper (`ld-wrapper.sh`) fills with the directory of every store `.so` and `-L` store directory that holds a library it links; a binary linked without the wrapper has none, and needs an rpath of its own. Cargo instead puts every run of the build on the path, because its runs share one `target/<profile>` and it keeps one set for the whole build (`Compilation::native_dirs`). The test's own runs are enough: Cargo links a unit against the search paths of the build scripts in its closure only (`add_native_deps`, over `build_scripts.to_link`), so a library the test was linked against is found again through them. So a failing build script blocks only the tests that depend on it, and an edit re-runs only the tests below it. A test that loads, by name, a library that a build script outside its closure placed (an unrelated crate's) passes under `cargo test` and fails here: make that crate a dev-dependency, or, for a library from nixpkgs, put it in the package's `test.env` or inputs.

  The variable that holds it is the test process's platform's, not always the build machine's: the target runner's when it declares one (wine reads `WINEPATH`, `;`-separated, and finds no DLL on the Unix `PATH` or `LD_LIBRARY_PATH`; checked with wine 11.0), else the target's traits (`dylibPathVar`: `LD_LIBRARY_PATH` on Linux, `PATH` on Windows run natively), and none for wasm.

  Cargo on a Linux host sets `LD_LIBRARY_PATH` for a Windows target runner too, so a Windows test that loads a DLL its build script built fails under `cargo test` with wine and passes in breakbulk (`windows-dll-*` in `tests/presets/extra-targets.nix`).

  The variable of recorded processes (compiles and build-script runs, which always run on the build machine) is the build machine's, one constant (`breakbulk_unit::splice::DYLIB_PATH_VAR`, re-exported by breakbulk-format as `HOST_DYLIB_PATH_VAR`). It succeeds on exit 0. The output goes to the build log and to `$log` in `$TMPDIR`, never to `$out` (an empty directory), so that a passing run is reproducible under `nix build --rebuild`. After a passing run, a subshell runs the run's `postRun`, its layers' snippets concatenated (`postRunSnippets` in `lib/test-runs.nix`). A coverage variant's (`breakbulk.variants.coverage`, `lib/variants.nix`) comes first, from its `memberDefaults.variant.<v>` layer: it moves the profiles into `$out/profraw`, renamed by content, as `LLVM_PROFILE_FILE`'s `%p` (set by its `coverage` entry of `preRun`) is a process ID. Dynamic-derivation mode's runs use the same snippets.
- **Skipped tests:** a predicted test the plan lacks gets a test-run stub that succeeds and logs the reason.
- **Test arguments:** [`test.args`](../../reference/options/packages.md#packagesnametestargs) and `test.binaries.<binary>.args` are passed to the binary (`--include-ignored` runs `#[ignore]` tests too). They are part of the test-run derivation, so changing them re-runs only the affected runs. `enable = false` leaves a binary's run out of `repo.checks`. `test.binaries.<binary>.env` adds to `test.env` for that binary's run. The test runner sets the thread count: `testRunners.direct` sets `RUST_TEST_THREADS=$NIX_BUILD_CORES` if nothing before set it (`[env]`, the run's `env`); `testRunners.nextest` writes a tool config file whose default profile sets `test-threads` to `$NIX_BUILD_CORES` and passes it (`--tool-config-file`), which nextest ranks below the project's configuration and below `NEXTEST_TEST_THREADS`, so both still win ([threads](../products.md#tests)).
- **Test apps:** each test binary also gets a runnable app with the test run's working directory, environment, wrapper and target runner (not its test runner: the app starts the binary itself), run on the user's machine. It is the escape hatch for tests that need network, and the way to rerun one binary under a debugger or with a filter. Network access inside `nix flake check` (through a fixed-output test run) is a possible later addition; impure derivations are not used.
- **Test runners.** What starts the binary is the run's test runner ([`test.runner`](../../reference/options/packages.md#packagesnametestrunner)), a function from the run's facts to a shell snippet (`lib/test-runners.nix`), called in `runScript` of `mkTestRuns` after the environment, `preRun` and the working directory are set up; breakbulk tees its output to `$log` and adds the hint and `postRun`. `testRunners.direct`, the default, runs the binary itself. `testRunners.nextest` writes the `binaries-metadata` and `cargo metadata` files that nextest's reuse-build mode reads, with jq at build time, so per-test retries, timeouts, test groups and default filters from the nextest config apply; each binary is still its own test run. Its metadata lists every path package of the test plan with its Cargo targets (the plan's `pathPackages`, which the wrapper's `breakbulk-root.json` carries by name, and a run reads through a small derivation of its own, `pathPackagesOf`, only when its runner names it), so filters with `package()`, `binary()` and `binary_id()` match as under Cargo. Only the tested package's entry carries its `CARGO_PKG_*` values and a manifest, in the run's working directory; nextest reads nothing else from the others, which are listed by name, under the scratch workspace root, so a version or description change elsewhere does not re-run the run, and a narrowed `"run"` view leaves the test view out of its closure. A filter is only evaluated for the run's own binary, so for `deps()` and `rdeps()` the metadata has an edge to the tested package from each package that reaches it, and from it to each package it reaches, over the edges the variant's units use. The standard library's packages under `-Zbuild-std` are not listed, as `cargo metadata` does not list them. The cost: adding or renaming a target anywhere in the workspace re-runs every nextest run, as nextest checks `binary()` and `binary_id()` names against every target, and which ones a configuration names is nextest's to parse.
- **Doctests:** one derivation per library crate, from the test plan's traced `rustdoc --test` command. Inputs are the crate's `rlib`, its dependencies with test-plan features, and the source view. Cargo gives `rustdoc --test` an `-L` for every run in the invocation, sorted by value. The derivation keeps only the runs of its platform in its own closure, by the same rule as test runs: it depends on their `flags` outputs and rebuilds the sorted list from them at build time. Its dynamic-library path, which Cargo fills with every host run's in-`out` search paths, keeps the host runs in its closure (those of the proc macros rustdoc loads). It gets no `-l`. It runs under the runner of its platform, as Cargo picks the runner by compile kind: a library's doctest runs under the target's runner; a proc macro's doctest is a host unit (no `--target`), so it runs on the build machine with no runner. As a test run, it gets a fresh, empty `HOME` at `$TMPDIR/home` (`breakbulk-doctest` puts it in layer 1, so `env` can replace it) and `RUST_TEST_THREADS`, but from breakbulk-doctest, not from `preRun`: rustdoc runs the examples itself, so the run settings `wrapper`, `runner`, `preRun` and `stages` do not apply to doctests, and under `test.doctest` they are an error (`doctestAssertions` in `lib/repository.nix`). Its `args`, `env` and `path` (as `PATH`) come from the doctest run's settings (`doctestConfig`, the rendered doctest's `test`). Its output goes to the build log and `$TMPDIR`, and `$out` is empty. The doctest run's `postRun` snippets become one script (the doctest's `postRun`, with stdenv's basic tools on `PATH`), which `breakbulk-doctest` runs after passing doctests. It appears in `repo.checks`. There is no cutoff, because compiling and running happen in one rustdoc process. If the toolchain cannot run doctests for a cross target, the derivation is a stub that logs why.
- **Benches:** `cargo test --no-run` builds no benches, so the test plan has none. Bench binaries come only from the bench variant (`cargo bench --no-run`, bench profile), exposed for running outside Nix. Each also has a run, as a test binary has (`mkTestRuns` with `kind = "bench"` over the bench plan), with the [`bench`](../../reference/options/packages.md#packagesnamebench) run settings, whose `args` start with `--test`; the enabled ones are checks of the variant. Timed runs never happen inside Nix.

## Documentation

Each variant on each target has a doc plan, traced from `cargo doc` (with `--no-deps` under [`docs.noDeps`](../../reference/options/workspaces.md#workspacesnamevariantsnamedocsnodeps), the default), and one docs derivation, `target.<triple>.variants.<v>.docs`. The plan is traced only when the docs are used.

- **Units.** rustdoc reads its dependencies' metadata, so Cargo checks them (`compute_deps_doc` in cargo's `unit_dependencies.rs`: check mode for libraries, a real build for proc macros) and runs their build scripts. These units are the plan's units, and they are the same derivations as a check variant's of the same profile and features: Cargo hashes no "doc" into their `-C metadata`. A variant's doc plan is traced without its wrappers, so a clippy variant's members' units are the check variant's too.
- **One derivation.** rustdoc writes each crate into one folder and merges the cross-crate files there in place: the search index, `crates.js`, `src-files.js` and the implementor lists under `trait.impl/` and `type.impl/` (`write_shared` in rustdoc's `html/render/write_shared.rs`, with the default `--merge=shared`). The options that write each crate's part apart and merge them in a final step (`--write-doc-meta-dir`, `--read-doc-meta-dir`, formerly `--parts-out-dir`, `--include-parts-dir` and `--merge`) are unstable in rustdoc 1.99, and Cargo uses them only with `-Zrustdoc-mergeable-info`. So the docs derivation (`breakbulk-unit` with a `docs` value) runs every traced rustdoc command in turn with `-o $out`. As Cargo does, it removes the crate's own directory first; it removes rustdoc's `.lock` at the end.
- **Order.** rustdoc links to another crate's items only when that crate's directory is already in the output folder when it starts (`ExternalCrate::location` in rustdoc's `clean/types.rs`); otherwise a crate without `html_root_url` gets no link. Cargo documents a dependency before its dependents when it documents both, but under `--no-deps` it does not order the members' rustdocs, so whether `util`'s docs link to `base`'s depends on which ran first. Each doc unit of the plan lists the doc units of the documented crates it reads (its `--extern`s) as its `after` edges, and the docs derivation runs the units in that order, otherwise by crate name: every link that can resolve does, and the result does not change from one plan to the next. Cargo passes `--extern-html-root-url` only with `-Zrustdoc-map`.
- **One folder.** With `--target`, Cargo documents a proc macro into its host directory, `target/doc`, and every other crate into `target/<triple>/doc`, so the target's pages do not link to the proc macro's. breakbulk always passes `--target`, so that rustflags stay off host units; the docs derivation writes every crate into its one output, as Cargo does without `--target`.
- **Inputs.** Each command's dependency directory holds the `rmeta` of every crate below it, and a proc macro's library; its build scripts' `flags` give its `--cfg`, `--check-cfg` and env, as for a compile. The derivation names all of them as inputs: it reads no manifests.

A crate outside the workspace (a registry or git crate, documented with `docs.noDeps = false`) has its source pages describe its source by its absolute path, as under Cargo; here that is the crate's store path, so the docs reference those sources.
